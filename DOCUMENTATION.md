## 1. Что это и как устроено

Пользователь подключается к **одному постоянному адресу** (ваш сервер, порт 443, VLESS+Reality). За ним
балансировщик держит пул узлов из ваших подписок, постоянно проверяет их и направляет трафик через лучший.
Пользователь не выбирает узел и не замечает переключений.

```
 клиент ──VLESS+Reality:443──►  sing-box (шлюз)  ──selector "proxy"──►  узел 1 ─┐
 (один адрес)                        ▲                                   узел 2 ─┼─► интернет
                                     │ Clash API (переключение)          ...    ─┘
                              контроллер (balancer)
                              ├─ подписки (раз в 30 мин) ──► PostgreSQL
                              ├─ проверки: tier1 / tier2 / tier3 / watchdog
                              ├─ выбор лучшего узла, failover
                              └─ /status, /metrics, /healthz, Telegram
```

Компоненты внутри одного контейнера `balancer`:

| Компонент | Роль |
|---|---|
| **sing-box 1.11.4** | Принимает пользователей (VLESS+Reality), содержит все узлы как outbound-ы и selector `proxy`. Запускается как дочерний процесс контроллера, при падении перезапускается. |
| **контроллер (Go)** | Скачивает подписки, генерирует конфиг sing-box, проверяет узлы, переключает selector, шлёт алерты, отдаёт HTTP-статус. |
| **PostgreSQL 16** | Хранит пользователей, узлы, историю проверок и переключений. |

Как проверяется конкретный узел: у sing-box есть локальный socks-вход `127.0.0.1:2080`, у каждого узла свой
логин `probe-<tag>` со случайным паролем (новый при каждом запуске). Запрос через логин `probe-X` всегда
уходит через узел X. Так контроллер измеряет именно этот узел, а не «текущий лучший».

Важная особенность: **все пользователи выходят через один общий лучший узел**. Это упрощает систему, но значит,
что нагрузка всех пользователей приходится на один апстрим.

## 2. Что нужно до начала

- Сервер с Linux, публичным IP (или доменом) и свободным портом **443/tcp**. Хватит 1 vCPU и 1 ГБ RAM для
  десятков пользователей и сотни узлов.
- Docker и Docker Compose v2 (`docker compose version`).
- Исходящий доступ сервера к: вашим подпискам, `gstatic.com`, `cloudflare.com`, `youtube.com`,
  `speed.cloudflare.com`, `ghcr.io` (один раз, для сборки образа), `proxy.golang.org` и `sum.golang.org`
  (при сборке образа).
- Одна или несколько ссылок подписок (base64 или список ссылок с `vless://`, `vmess://`, `trojan://`, `ss://`,
  `hysteria2://` / `hy2://`).
- Необязательно: Telegram-бот для алертов.

## 3. Установка шаг за шагом

### 3.0. Быстрая установка одним файлом (рекомендуется)

`install.sh` содержит весь проект внутри. На чистом Linux-сервере (Ubuntu/Debian, root, порты 443 и 8080 свободны):

```bash
sudo bash install.sh                                  # спросит адрес сервера и подписку
sudo bash install.sh -y --sub https://адрес-подписки  # без вопросов
```

Установщик: ставит Docker (если нет), генерирует ключи Reality и пароль БД, подбирает сайт-маскировку реальной проверкой
соединения, пишет `config.yaml` и `.env`, собирает и запускает систему, проверяет конфиг, создаёт пользователя `admin`
и печатает ссылку для клиента и токен панели. Подписку можно не указывать: `vpnb subs add АДРЕС` добавит её позже
(пока подписок нет, трафик пользователей отклоняется).

Параметры: `--dir` (по умолчанию `/opt/vpn-balancer`), `--host`, `--sub` (можно несколько), `--user`, `--port`, `--sub-server`
(выдача личных подписок на порту 8081), `--tg-token`/`--tg-chat`, `-y`.

После установки появляется команда `vpnb` (то же, что `balancer` внутри контейнера, раздел 6c): `vpnb status`, `vpnb nodes`, `vpnb adduser ИМЯ`, `vpnb token`.

| Действие | Команда |
|---|---|
| Обновить код (настройки, пользователи и данные сохраняются) | `sudo bash install.sh update` (новый install.sh) |
| Состояние | `sudo bash install.sh status` |
| Остановить | `sudo bash install.sh uninstall` |
| Удалить вместе с данными | `sudo bash install.sh uninstall --purge` |
| Только распаковать проект | `bash install.sh extract ПАПКА` |

Для сборки нужен доступ к ghcr.io, Docker Hub и proxy.golang.org. Дальше идёт ручная установка, если установщик не подходит.

### 3.1. Распаковать проект

```bash
unzip vpn-balancer-fixed.zip
cd vpn-balancer
```

### 3.2. Пароль базы данных

```bash
cp .env.example .env
```

В `.env` замените значение `DB_PASSWORD` на длинный случайный пароль. **Только буквы и цифры**, пароль
вставляется в URL подключения, спецсимволы (`@`, `/`, `:`, `#`) его ломают. Удобно так:

```bash
echo "DB_PASSWORD=$(openssl rand -hex 16)" > .env
```

### 3.3. Ключи Reality

```bash
docker run --rm --entrypoint sing-box ghcr.io/sagernet/sing-box:v1.11.4 generate reality-keypair
# PrivateKey: ....
# PublicKey:  ....
openssl rand -hex 8        # это short_id
```

Приватный ключ остаётся только на сервере. Публичный ключ и short_id попадают в ссылки пользователей.

### 3.4. Конфиг

```bash
cp config.example.yaml config.yaml
nano config.yaml
```

Обязательно заполните (значения в `<...>` система считает незаполненными и не запустится):

- `subscriptions`: ваши ссылки подписок.
- `public_host`: IP или домен сервера, куда будут подключаться клиенты.
- `reality.private_key`, `reality.public_key`, `reality.short_id`: из шага 3.3.
- В `database_url` пароль берётся из переменной `${DB_PASSWORD}`, менять ничего не нужно, если вы
  используете `docker-compose.yml` как есть.

Остальное можно оставить по умолчанию, описание всех параметров в [разделе 5](#5-справочник-по-configyaml).

`handshake_server` (по умолчанию `www.microsoft.com`) это настоящий HTTPS-сайт, под который
маскируется Reality. Выберите популярный сайт с TLS 1.3 и HTTP/2, не заблокированный у ваших пользователей.
Проверьте его с вашего сервера до запуска:
`echo | openssl s_client -connect САЙТ:443 -servername САЙТ -tls1_3 -groups X25519 2>&1 | grep -E "Protocol|Cipher"`
(должны быть TLSv1.3 и шифр, а не ошибка).

### 3.5. Запуск

```bash
docker compose up -d --build
docker compose logs -f balancer
```

Первая сборка скачивает Go-зависимости и образ sing-box. После старта в логах должны появиться строки вида
`subs: <домен>: N nodes` и `subs: refresh done, N nodes parsed`. Если запуск остановился сообщением `config: ... is not
set`, значит, остался незаполненный параметр.

### 3.6. Проверка, что всё работает

```bash
curl -s http://127.0.0.1:8080/healthz          # ok
curl -s http://127.0.0.1:8080/status | head -40
```

В `/status` у каждого узла есть `score`. Через 3-4 минуты после старта (первый цикл tier2) у живых узлов
он больше нуля, а один узел помечен `"current": true`. Порт 8080 слушает только `127.0.0.1` сервера, снаружи
он недоступен (и это правильно, см. [безопасность](#10-безопасность)).

### 3.7. Файрвол

Откройте только 443/tcp. 8080 наружу открывать не нужно.

```bash
# пример для ufw
ufw allow 443/tcp
```

## 4. Пользователи и подключение клиентов

Все команды выполняются внутри работающего контейнера:

```bash
alias bal='docker compose exec balancer balancer -c /etc/balancer/config.yaml'
```

| Команда | Что делает |
|---|---|
| `bal adduser alice` | Создаёт пользователя. Первая строка вывода: личная ссылка `vless://...` на балансировщик. Если включена выдача подписок (`sub_listen` и `sub_public_url`), второй строкой идёт адрес личной подписки |
| `bal users` | Список пользователей, их статус (`enabled`), ссылки на балансировщик и на подписку |
| `bal deluser alice` | Отключает пользователя (запись остаётся, `enabled=false`); его подписка тоже перестаёт открываться |
| `bal check` | Проверяет `config.yaml` (параметры, правила фильтра) без запуска чего-либо и без базы |

Ссылка одна на пользователя и постоянная. Она содержит адрес сервера, порт, UUID пользователя и параметры
Reality. Отправьте её пользователю. Повторно показать ссылку можно командой `bal users`.

**Когда пользователь начинает работать.** Контроллер сверяет список пользователей каждые 30 секунд. Изменение
состава пользователей приводит к перезагрузке sing-box, которая рвёт все текущие соединения на пару секунд.
Перезагрузки не чаще, чем раз в `min_reload_interval` (2 минуты), поэтому новый пользователь может появиться
с задержкой до 2-2,5 минут. Если добавляете нескольких, добавьте их подряд: они применятся одной перезагрузкой.

**Клиенты**, которые поддерживают VLESS+Reality с `xtls-rprx-vision`:

- Android: v2rayNG, Hiddify, NekoBox
- iOS / macOS: Streisand, Shadowrocket, Hiddify, V2Box
- Windows: v2rayN, Hiddify, NekoRay
- Linux: Hiddify, sing-box, v2rayN

Импорт: скопировать ссылку и в клиенте выбрать «Импорт из буфера обмена». Проверьте, что клиент не
добавляет собственный балансировщик или правила, которые ломают схему «один адрес».

Ссылка, которую выдаёт `adduser`, имеет вид:

```
vless://<uuid>@<public_host>:<inbound_port>?encryption=none&flow=xtls-rprx-vision&security=reality&sni=<handshake_server>&fp=chrome&pbk=<public_key>&sid=<short_id>&type=tcp#<имя>
```

Если вы меняете `public_host`, порт, ключи Reality или `short_id`, **все выданные ссылки перестают
работать**, пользователям нужно выдать новые (`bal users`).

### 4.1. Подписка для пользователя

Вместо одной ссылки пользователю можно выдать **личный адрес подписки**. В клиенте (Hiddify, v2rayN, Streisand,
Shadowrocket и другие) он добавляется как обычная подписка: клиент скачает список серверов и будет обновлять его сам.

Содержимое подписки:

1. **Первая строка: балансировщик**, личная ссылка пользователя (название берётся из `gateway_name`).
2. Дальше **все серверы, которые балансировщик загрузил из подписок**, но только те, чей выход проверен
   и находится не в запрещённой стране (раздел 6a). Название каждого начинается с измеренной страны выхода,
   например `[DE] Германия`. Узлы с неизвестным или запрещённым выходом и узлы, которых ещё не успели проверить,
   в подписку не попадают.

Как включить. В `config.yaml`:

```yaml
sub_listen: 0.0.0.0:8081                    # где слушать (пусто = выдача подписок выключена)
sub_public_url: https://vpn.example.com:8081 # как адрес выглядит снаружи, нужен для вывода adduser/users
sub_tls_cert: /etc/balancer/fullchain.pem   # необязательно: HTTPS без отдельного прокси
sub_tls_key: /etc/balancer/privkey.pem
gateway_name: Балансировщик
```

Откройте порт в файрволе и в `docker-compose.yml` (там есть закомментированная строка `8081:8081`). Адрес
подписки вида `https://vpn.example.com:8081/sub/<секрет>`, секрет у каждого пользователя свой.

Что важно знать:

- **Подписка содержит ссылки на серверы провайдера вместе с их ключами.** Тот, у кого есть адрес подписки,
  видит их. Выдавайте её только тем, кому доверяете, и обязательно по **HTTPS** (`sub_tls_*` или свой прокси):
  по обычному HTTP секрет и ссылки видны по пути. Без TLS в логе при старте будет предупреждение.
- Подписку нельзя угадать подбором: после 20 неверных запросов за 10 минут адрес получает ответ 429.
  Неверный секрет и отключённый пользователь дают одинаковый ответ 404.
- Чтобы увидеть содержимое глазами: добавьте `?raw=1` к адресу (выводится список без base64).
- Если пользователь обновляет подписку, он получает актуальный набор: узлы, чей выход перестал быть допустимым,
  из неё пропадают.
- Подписка выдаёт узлы с их собственным адресом, поэтому трафик через такой узел **не проходит проверку фильтра
  и страны выхода, которые делает балансировщик** для основной ссылки. Основной путь пользователя это первая строка.

## 5. Справочник по config.yaml

Длительности пишутся как `30s`, `5m`, `48h`. В значениях можно использовать переменные окружения
(`${DB_PASSWORD}`). Если задана переменная окружения `DATABASE_URL`, она перекрывает `database_url`.

### База и подписки

| Параметр | По умолчанию | Описание |
|---|---|---|
| `database_url` | нет | Строка подключения к PostgreSQL. |
| `subscriptions` | нет | Список URL подписок. Обязателен для запуска. |
| `sub_user_agent` | `sing-box` | User-Agent при скачивании подписок (некоторые провайдеры отдают разное содержимое разным клиентам). |
| `sub_refresh` | `30m` | Как часто обновлять подписки. |
| `node_identity` | `endpoint` | Как считать узлы. `endpoint`: ссылки с одинаковыми параметрами подключения (адрес, порт, UUID, ключи) сливаются в один узел, различающийся только названием. `link`: каждая ссылка подписки остаётся отдельным узлом, даже если параметры совпадают. Нужен, чтобы использовать **все** ссылки подписки и увидеть измеренную страну каждой. |
| `node_grace` | `48h` | Сколько узел остаётся в пуле после исчезновения из подписок. Защищает от кратковременных сбоев провайдера. |

### Вход для пользователей

| Параметр | По умолчанию | Описание |
|---|---|---|
| `public_host` | нет | Адрес сервера для ссылок пользователей. Обязателен. |
| `inbound_port` | `443` | Порт VLESS+Reality. Если меняете, поменяйте и проброс в `docker-compose.yml`. |
| `reality.private_key` | нет | Приватный ключ. Обязателен. |
| `reality.public_key` | нет | Публичный ключ (для ссылок). Обязателен. |
| `reality.short_id` | нет | 8 байт в hex. Обязателен. |
| `reality.handshake_server` | `www.microsoft.com` | Сайт для маскировки. |
| `reality.handshake_port` | `443` | Его порт. |

### sing-box и служебное

| Параметр | По умолчанию | Описание |
|---|---|---|
| `singbox_bin` | `sing-box` | Путь к бинарнику (в образе `/usr/local/bin/sing-box`, в PATH). |
| `work_dir` | `/var/lib/balancer` | Где хранится сгенерированный конфиг sing-box (том `balancer-data`). |
| `clash_api` | `127.0.0.1:9090` | Внутренний API sing-box, через него переключается узел. Только localhost. |
| `test_port` | `2080` | Локальный socks-вход для проверок узлов. Только localhost. |
| `min_reload_interval` | `2m` | Минимальная пауза между перезагрузками sing-box. |
| `http_listen` | `127.0.0.1:8080` | Адрес HTTP-интерфейса статуса. В примере задан `0.0.0.0:8080` (внутри контейнера), наружу он проброшен только на `127.0.0.1` сервера. |

### Проверки и выбор

| Параметр | По умолчанию | Описание |
|---|---|---|
| `tier1_interval` | `1m` | TCP-подключение ко всем узлам. |
| `tier2_interval` | `3m` | Реальные HTTPS-запросы через узел. |
| `tier3_interval` | `45m` | Тест скорости. |
| `tier3_top` | `5` | Сколько лучших узлов проверять на скорость. |
| `watch_interval` | `5s` | Проверка текущего узла. |
| `probe_urls` | gstatic, cloudflare, youtube (`generate_204`) | Сайты для tier2 и watchdog. **Добавьте сайты, важные вашим пользователям.** Узел считается рабочим, если ответило большинство. |
| `speed_url` | `https://speed.cloudflare.com/__down?bytes=5000000` | Что скачивать в tier3 (5 МБ). |
| `baseline_addrs` | `1.1.1.1:443`, `8.8.8.8:443`, `9.9.9.9:443` | Адреса для проверки, что у самого сервера есть интернет. |
| `tier2_concurrency` | `20` | Сколько узлов проверять параллельно. |
| `switch_margin` | `1.15` | Во сколько раз новый узел должен быть лучше текущего, чтобы переключиться. |
| `switch_confirm` | `3` | Сколько циклов tier2 подряд это должно выполняться. |

### Страна выхода

| Параметр | По умолчанию | Описание |
|---|---|---|
| `exit_check` | `true` | Определять, из какой страны узел реально выходит в интернет, и не пускать пользователей на узлы с выходом в запрещённой или неизвестной стране. Выключайте только для тестов. |
| `blocked_exit_countries` | `RU UA BY CN IR SY KP TM CU MM` | Двухбуквенные коды (ISO 3166-1) стран, выход в которые запрещён. Пустой список `[]` означает «ничего не запрещать». |
| `geo_urls` | ipinfo.io, api.country.is, ifconfig.co | Сервисы, которые отвечают, из какой страны пришёл запрос. Опрашиваются **через сам узел**. Понимаются ответы JSON (`country`, `country_code`, `countryCode`, `country_iso`) и простой текст `DE`. |
| `geo_ttl` | `6h` | Через сколько повторять определение страны. |
| `geo_blocked_ttl` | `30m` | Через сколько заново измерить узел, у которого выход оказался в запрещённой стране («карантин» по стране до следующей проверки). |

### Правила фильтра трафика пользователей

| Параметр | По умолчанию | Описание |
|---|---|---|
| `rules` | пусто | Список правил (раздел 6b). Проверяются сверху вниз, срабатывает первое подошедшее. |
| `default_action` | `proxy` | Что делать с трафиком, который не подошёл ни под одно правило: `proxy` (через балансировщик) или `block` (режим белого списка). Значения `direct` нет намеренно: сервер находится в России и не должен быть выходом по умолчанию. |

|---|---|---|
| `sub_listen` | пусто | Адрес, на котором отдаются подписки (`/sub/<секрет>`). Пусто значит «выключено». |
| `sub_public_url` | пусто | Внешний адрес для вывода `adduser`/`users`. |
| `sub_tls_cert`, `sub_tls_key` | пусто | Сертификат и ключ для HTTPS. |
| `gateway_name` | `Балансировщик` | Название первой строки подписки и ссылки на шлюз. |

## 6. Как система выбирает узел

### 6.1. Подписки и пул узлов

- Каждые `sub_refresh` контроллер скачивает все подписки (3 попытки на каждую), разбирает ссылки и
  сохраняет узлы в БД.
- Формат подписки определяется автоматически: обычный список ссылок или base64 (любой вариант, в том числе
  с переносами строк).
- **ID узла** это sha1 от его канонического описания. Переименование узла в подписке его не меняет,
  история проверок сохраняется. Одинаковые узлы из разных подписок считаются одним.
- Узел, исчезнувший из подписок, остаётся в пуле ещё `node_grace`.
- Не поддерживаются и отбрасываются при разборе: Clash YAML, sing-box JSON, tuic, wireguard, транспорты
  xhttp / kcp / quic, TCP с HTTP-обфускацией, ss с plugin.
- Если `sing-box check` отвергает отдельный узел, он исключается из конфига и попадает в лог
  (`core: node XXXXXXXXXX rejected by sing-box check, excluded: ...`). Остальные узлы работают.

### 6.2. Четыре вида проверок

| Проверка | Интервал | Что делает |
|---|---|---|
| **Tier 1** | 1 мин | TCP-подключение к каждому узлу. UDP-протоколы (hysteria2) пропускаются. |
| **Tier 2** | 3 мин | HTTPS-запросы через узел к каждому из `probe_urls`. Узел рабочий, если ответило большинство. Измеряется задержка. |
| **Tier 3** | 45 мин | Скачивание 5 МБ через топ-5 узлов, измерение скорости. |
| **Watchdog** | 5 с | Проверка текущего узла. Два сбоя подряд дают немедленный failover и сброс соединений. |

### 6.3. Оценка узла

```
score = 100 × успешность
        − min(задержка_ewma / 10, 40)
        − min(джиттер / 20, 10)
        + бонус_скорости (до +10, достигается на 40 Мбит/с)
```

Оценка равна **0**, если успешность в окне последних проверок ниже 0,6 или было 2 сбоя подряд.

### 6.4. Когда происходит переключение

- **Срочно (failover):** текущий узел получил оценку 0, то есть упал. Переключение сразу на лучший из живых,
  активные соединения сбрасываются, чтобы клиенты переподключились заново.
- **Плановое улучшение:** другой узел должен быть лучше текущего минимум в `switch_margin` (1,15) раза
  **`switch_confirm` (3) цикла tier2 подряд**. Если преимущество пропало хотя бы в одном цикле, счётчик
  обнуляется. Это защищает от «дёргания» между похожими узлами.
- При равных оценках побеждает узел с меньшей задержкой, затем по ID (выбор детерминирован).

### 6.5. Карантин

Узел, провалившийся 3 раза подряд, уходит в карантин: 1, 2, 4, 8, 16, затем максимум 30 минут. Во время
карантина он не проверяется. Один успешный tier2 снимает карантин.

### 6.6. Защита от ложных тревог

- **Базовая связность.** Перед записью результатов проверяется TCP до `baseline_addrs`. Если у самого
  сервера нет интернета, результаты отбрасываются, узлы не наказываются, переключений нет, приходит алерт.
- **Перезагрузка sing-box.** Проверки, которые шли во время перезагрузки, отбрасываются. Watchdog
  первые 5 секунд после перезагрузки сбои не считает.
- **Непроверенные узлы.** Алерт «все узлы недоступны» не срабатывает, пока узлы ни разу не проверялись.

### 6.7. Что видит пользователь при failover

Соединения сбрасываются, клиент переподключается к тому же адресу, трафик идёт уже через новый узел. Обычно это
пауза в несколько секунд, страницы и видео продолжают работать после повторного запроса. Долгие загрузки и
стримы могут оборваться.

### 6.8. Перезапуск системы

При старте контроллер продолжает с последнего выбранного узла (из таблицы `switches`). Если узлы уже есть в
БД, система поднимается сразу, не дожидаясь скачивания подписок. Если БД пуста (первый запуск), сначала
скачиваются подписки.

## 6a. Страна выхода узла

Узел в подписке часто только «прокладка» (вход в России, дальше цепочка). Название в подписке ничего не
гарантирует: метка «США» может вести на выход в России. Поэтому балансировщик **сам измеряет**, откуда узел
выходит в интернет:

1. После успешной проверки узла (tier 2) он отправляет через этот узел запросы к сервисам из `geo_urls`
   (по умолчанию ipinfo.io, api.country.is, ifconfig.co). Сервис видит адрес **последнего узла цепочки** и называет его страну.
   Берутся два ответа; если хоть один указывает страну из запрещённого списка, узел считается находящимся в ней
   (выбирается безопасная сторона).
2. Результат записывается в базу (`nodes.exit_country`, `nodes.exit_ip`) и повторяется раз в `geo_ttl` (6 часов).
3. Если выход в стране из `blocked_exit_countries`, **узел исключается**: он не попадает в выбор для пользователей
   (в sing-box он вообще не входит в `proxy`), не выдаётся в подписке, и приходит Telegram-алерт.
4. Пока страна **неизвестна** (ещё не измерена, сервисы не ответили), узел тоже не используется. Это намеренно:
   лучше подождать минуту после старта, чем отправить человека в цензурируемую страну.
5. Узел из запрещённой страны **не выбрасывается совсем**, а уходит в «карантин» по стране (в `/status` он помечен
   `quarantined: true`, `allowed: false`): проверки продолжаются, страна измеряется заново через `geo_blocked_ttl`
   (30 минут), и если выход изменился на допустимый, узел возвращается в работу.
6. Если **текущий** узел при проверке оказался в запрещённой стране, контроллер переключает пользователей на лучший допустимый.

**Все ссылки подписки как отдельные узлы.** По умолчанию ссылки с совершенно одинаковыми параметрами подключения
считаются одним узлом (для сервера это одно и то же соединение, проверять 26 копий смысла нет). Если нужно использовать
каждую ссылку подписки отдельно (например, провайдер выдаёт 100+ ссылок и вы хотите видеть и использовать каждую),
включите `node_identity: link`: тогда каждая ссылка станет узлом со своей оценкой, своим измерением страны и своей
строкой в пользовательской подписке, а узлы с выходом в запрещённых странах отфильтруются автоматически.
Если несколько ссылок ведут на одну и ту же машину, они покажут одинаковую страну и одинаковую задержку.

Если у всех узлов выход запрещён или неизвестен, трафик пользователей **отклоняется**, а не идёт напрямую
через сервер. Это то самое «ни в коем случае не подключать пользователя через себя»: сервер находится в России, и его
собственный выход не должен становиться запасным вариантом. Приходит алерт «Нет допустимых узлов».

Посмотреть результат: `curl -s 127.0.0.1:8080/status | jq '.nodes[] | {name, exit_country, exit_ip, allowed}'`.
Поле `allowed` значит «может нести трафик пользователей». Метрика `balancer_nodes_excluded_by_country`.

**Как проверить сервис в целом**, если вы не доверяете названиям в подписке: сравните `name` и `exit_country`
в `/status`. Одинаковые ссылки с разными названиями (в тестовой подписке 108 ссылок вели на 5 серверов) сливаются
в один узел, потому что для сервера это одно и то же соединение. В `/status` вы увидите реальное число серверов.

**Не определяется страна?** Сервисы из `geo_urls` должны быть доступны **через узлы**. Если провайдер блокирует часть
из них, добавьте свой сервис, который отдаёт JSON с полем `country` или двухбуквенный код. В логе при определении
пишется `geo: <узел> exits in DE (1.2.3.4)`.

## 6b. Правила фильтра: что пускать напрямую, что блокировать

По умолчанию **весь трафик пользователя идёт через балансировщик**. Исключения задаются списком `rules` в
`config.yaml`. Правила применяются только к трафику пользователей (не к проверкам узлов) и вычисляются сверху вниз,
**срабатывает первое подошедшее**. Поэтому конкретные правила ставьте выше общих.

```yaml
rules:
  - action: proxy           # исключение из правила ниже: этот поддомен идёт через балансировщик
    match:
      - "*.gov.ru"
  - action: direct          # идти напрямую через сервер (он в России: полезно для российских сайтов)
    match:
      - "*.ru"              # любой домен в зоне .ru
      - "*.xn--p1ai"        # зона .рф (в punycode)
      - "sberbank.com"      # ровно этот домен
      - "10.20.0.0/16"      # сеть
      - "100.200.255.7"     # один адрес
  - action: block           # отклонить
    match:
      - "keyword:tracker"   # в имени есть слово
      - "port:25"           # SMTP
      - "port:6881-6999"    # торренты
default_action: proxy       # остальное: через балансировщик
```

Порядок важен: `*.gov.ru` стоит выше `*.ru`, иначе до него дело не дойдёт.

Действия: `direct` (напрямую с сервера), `block` (отклонить соединение), `proxy` (через балансировщик).

**Что можно писать в `match`:**

| Запись | Значение |
|---|---|
| `*.ru` | любой домен зоны `ru` (и сам `ru`) |
| `*.example.com`, `.example.com` | `example.com` и все его поддомены |
| `example.com` | только этот домен |
| `ads*.example.com`, `?` | подстановка внутри имени (превращается в регулярное выражение) |
| `100.200.255.0/24`, `2001:db8::/32` | сеть (IPv4 и IPv6) |
| `1.2.3.4` | один адрес |
| `port:25`, `port:6881-6999` | порт или диапазон портов |
| `keyword:слово` | в домене есть это слово |
| `regex:^a.+b$` | регулярное выражение по домену |
| `domain:`, `suffix:`, `cidr:` | явная форма, если сомневаетесь |

Правила проверяются при запуске: опечатка в правиле останавливает запуск с понятным сообщением (проверить
заранее: `bal check`). Изменение правил применяется после перезапуска контроллера.

**Ограничения:**

- Правила по IP-адресам и сетям (`100.200.255.0/24`) срабатывают, **когда клиент сам подключается к IP-адресу**.
  Если клиент отправляет имя сайта, сервер его не переводит в IP для сравнения (это сделало бы запрос DNS с сервера в России
  и могло бы дать подмену). Для сайтов пишите правила по доменам.
- Домены с не-ASCII символами пишите в punycode (`xn--p1ai` вместо `рф`).
- Правило `direct` отправляет трафик с **IP-адреса сервера**: он российский, и со стороны сайтов это российский пользователь.
  Использовать для российских сервисов удобно, для остального нет.
- Если допустимых узлов нет, правила `proxy` превращаются в `block`, а `direct` и `block` продолжают работать как задано.
- `default_action: block` включает режим белого списка: пропускается только то, что разрешено правилами
  (`direct`/`proxy`), остальное отклоняется.

## 6c. Веб-панель, консольные команды и настройки на лету

Всем, что нужно для работы, можно управлять двумя способами: веб-панелью и командами. Оба работают с одним и тем же API
контроллера и одними и теми же настройками.

### Веб-панель

Панель встроена в бинарник (`ui.html`), отдельно ничего ставить не нужно. Она слушает на `http_listen` (по умолчанию
`127.0.0.1:8080` на сервере), наружу не проброшена. Открывать через SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 root@СЕРВЕР      # затем в браузере http://127.0.0.1:8080/
docker compose exec balancer balancer -c /etc/balancer/config.yaml token    # токен для входа
```

Токен создаётся при первом запуске и хранится в базе (таблица `settings`, ключ `admin_token`). Без него видны только `/status`,
`/metrics`, `/healthz` (как раньше), всё, что показывает секреты или что-то меняет, требует токена.

Вкладки:
- **Обзор**: текущий узел, закреплён ли он, сколько узлов живо/допущено/исключено по стране, последние переключения, кнопки «скачать подписки» и «перемерить страны».
- **Узлы**: таблица с оценкой, задержкой, страной выхода, статусом (допущен, карантин, мёртв), поиск и фильтры, кнопка «закрепить».
- **Настройки**: подписки, запрещённые страны, правила фильтра (добавить, удалить, порядок), действие по умолчанию, режим идентификации узлов, имя шлюза, адреса проверок, параметры переключения. Каждое поле проверяется перед сохранением.
- **Пользователи**: список, создание, включение/отключение, ссылка на шлюз и адрес личной подписки.

Панель не использует внешних скриптов и шрифтов, не вставляет данные как HTML, ставит `Content-Security-Policy`.

### Команды

В Docker: `docker compose exec balancer balancer -c /etc/balancer/config.yaml КОМАНДА` (дальше для краткости `balancer КОМАНДА`).
Команды управления обращаются к работающему контроллеру по `http_listen` с токеном из базы, поэтому ничего вводить не нужно.
`balancer help` печатает эту же справку.

| Команда | Что делает |
|---|---|
| `status` | сводка: текущий узел, число узлов, страны выхода, последние переключения |
| `nodes [-a] [--dead] [--excluded] [--country XX] [текст]` | список узлов (по умолчанию допущенные и живые, до 30; `-a` все) |
| `node ИМЯ` | подробности об узле (имя, часть имени или tag) |
| `switch ИМЯ` | закрепить узел вручную; закрепление действует, пока узел жив и допущен по стране, потом выбор снова автоматический |
| `unpin` | снять закрепление |
| `refresh` | скачать подписки сейчас |
| `recheck` | заново измерить страну выхода всех узлов |
| `users`, `adduser ИМЯ`, `deluser ИМЯ`, `enableuser ИМЯ`, `sub ИМЯ` | пользователи и их подписки |
| `get [КЛЮЧ]`, `set КЛЮЧ ЗНАЧЕНИЕ`, `reset КЛЮЧ` | настройки (ниже) |
| `rules list / add ДЕЙСТВИЕ ЗАПИСЬ… / del N / move N M / clear` | правила фильтра, например `rules add direct "*.ru" "*.su"` |
| `countries list / block XX… / allow XX…` | запрещённые страны выхода |
| `subs list [--show] / add АДРЕС / del N` | подписки (адреса по умолчанию скрыты) |
| `token` | токен панели |
| `check` | проверить config.yaml и правила, не запуская ничего |
| `run` | запустить контроллер (по умолчанию) |

Команды `set`/`rules`/`countries`/`subs` проверяют значение так же, как панель, и при ошибке ничего не меняют. Неизвестная команда печатает справку и завершается с кодом 2.

### Настройки на лету

Эти ключи хранятся в базе и **перекрывают config.yaml**; контроллер подхватывает изменения не позже чем через 10 секунд, перезапуск не нужен:

`subscriptions`, `blocked_exit_countries`, `exit_check`, `rules`, `default_action`, `node_identity`, `gateway_name`, `probe_urls`, `switch_margin`, `switch_confirm`.

Остальное (порты, ключи Reality, пути, БД) меняется только в config.yaml с перезапуском. Изменение правил, стран или набора узлов приводит к перезагрузке sing-box (не чаще `min_reload_interval`, кроме первого допустимого узла). `reset КЛЮЧ` убирает значение из базы: действующее значение сменится на config.yaml после перезапуска контроллера. Значения валидируются: `default_action direct` отклоняется (прямой выход по умолчанию запрещён), `switch_confirm` только 1-20, `switch_margin` 1.0-3.0 и т.д.

Примеры:
```bash
balancer set node_identity link          # каждая ссылка подписки отдельный узел
balancer countries block FR              # ещё одна запрещённая страна
balancer rules add block port:25         # запретить SMTP
balancer set switch_margin 1.5
balancer nodes --country DE
```

### HTTP API

Для автоматизации: заголовок `Authorization: Bearer ТОКЕН`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/overview` | снимок состояния и последние переключения |
| `GET`, `PUT /api/settings`, `DELETE /api/settings/{ключ}` | чтение, изменение (JSON `{ключ: значение}`, всё или ничего), сброс |
| `GET`, `POST /api/users`, `POST /api/users/{имя}/enable\|disable` | пользователи |
| `POST /api/pin` | `{"node":"имя"}` закрепить, пустое имя снимает |
| `POST /api/refresh`, `POST /api/recheck` | скачать подписки, перемерить страны |

После 10 неверных токенов за 10 минут с одного адреса API отвечает 429. Панель и API работают по обычному HTTP: держите `http_listen` на localhost и ходите через SSH-туннель. Если нужен доступ снаружи, ставьте перед ним TLS-прокси.

## 7. Мониторинг и алерты

### 7.1. HTTP-интерфейс

Адрес по умолчанию: `http://127.0.0.1:8080` (на сервере). Авторизации нет, см. [безопасность](#10-безопасность).

| Путь | Что возвращает |
|---|---|
| `/healthz` | `ok` (HTTP 200), если sing-box работает; иначе 503. Используется в healthcheck Docker. |
| `/status` | JSON: `net_down`, `switches`, список узлов. |
| `/metrics` | Метрики в формате Prometheus. |

Поля узла в `/status`:

| Поле | Смысл |
|---|---|
| `tag` | Внутренний идентификатор (`n-` + 10 символов ID). |
| `name`, `server`, `type` | Из подписки. |
| `score` | Текущая оценка (0 значит узел не используется). |
| `latency_ms`, `jitter_ms` | Сглаженная задержка и разброс. |
| `success_rate` | Доля успешных проверок в окне (0..1). |
| `speed_kbps` | Последний замер скорости (0, если не мерился). |
| `quarantined` | Узел в карантине. |
| `current` | Через него сейчас идёт трафик. |
| `exit_country`, `exit_ip` | Измеренная страна и адрес выхода (пусто, пока не измерено). |
| `allowed` | Может нести трафик пользователей (`exit_country` известна и не в `blocked_exit_countries`). |

Полезные запросы (нужен `jq`):

```bash
# текущий узел
curl -s 127.0.0.1:8080/status | jq '.nodes[] | select(.current)'

# топ-10 по оценке
curl -s 127.0.0.1:8080/status | jq -r '.nodes | sort_by(-.score)[:10][] | "\(.score)\t\(.latency_ms)ms\t\(.name)"'

# сколько узлов живо
curl -s 127.0.0.1:8080/status | jq '[.nodes[] | select(.score>0)] | length'
```

### 7.2. Метрики Prometheus

| Метрика | Смысл |
|---|---|
| `balancer_nodes_total` | Узлов в пуле. |
| `balancer_nodes_healthy` | Узлов с оценкой больше 0. |
| `balancer_switches_total` | Число переключений с момента запуска. |
| `balancer_net_down` | 1, если у сервера нет базовой связности. |
| `balancer_node_score{tag}` | Оценка узла. |
| `balancer_node_latency_ms{tag}` | Задержка узла. |
| `balancer_node_speed_kbps{tag}` | Скорость узла. |
| `balancer_node_current{tag}` | 1 у текущего узла. |

Разумные алерты: `balancer_nodes_healthy == 0` дольше 2 минут; `rate(balancer_switches_total[1h]) > 6`
(слишком частые переключения); `balancer_net_down == 1`. Чтобы Prometheus достучался до `8080`, либо
запускайте его на этом же сервере, либо поставьте обратный прокси с паролем. Не открывайте 8080 в интернет.

### 7.3. Telegram-алерты

1. В Telegram напишите @BotFather, команда `/newbot`, получите токен.
2. Напишите своему боту любое сообщение.
3. Узнайте ID чата: откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id":...}`.
4. Впишите `telegram_token` и `telegram_chat` в `config.yaml`, перезапустите.

Какие алерты приходят:

| Алерт | Когда | Не чаще |
|---|---|---|
| ⚠️ Failover: A → B | Переключение с одного узла на другой | раз в минуту |
| 🔴 Все узлы недоступны | Нет ни одного узла с оценкой больше 0 (при проверенных узлах) | раз в 15 мин |
| ⚠️ Подписка ... не обновляется | 3 и более неудачных обновления подряд (в тексте адрес без токена) | раз в 6 ч |
| ⚠️ У сервера нет базовой связности | Не проходит TCP до `baseline_addrs` | раз в 30 мин |
| 🔴 Пул узлов пуст | Нет ни одного узла в БД после старта | раз в час |

### 7.4. История в БД

```bash
docker compose exec postgres psql -U balancer balancer
```

```sql
-- последние переключения
SELECT ts, from_node, to_node, reason FROM switches ORDER BY ts DESC LIMIT 20;

-- как вёл себя узел за сутки (подставьте ID из таблицы nodes)
SELECT date_trunc('hour', ts) h, avg(latency_ms) FILTER (WHERE ok) lat,

FROM checks WHERE node_id = '...' AND ts > now() - interval '1 day' GROUP BY 1 ORDER BY 1;

SELECT id, name, type, server, last_seen FROM nodes ORDER BY last_seen DESC;
```

Таблица `checks` автоматически очищается: хранятся последние 7 дней.

## 9. Диагностика проблем

Порядок действий: `docker compose ps` → `docker compose logs --tail 200 balancer` → `curl 127.0.0.1:8080/status`.

| Симптом | Вероятная причина и что делать |
|---|---|
| Контейнер перезапускается, в логе `config: X is not set` | Не заполнен обязательный параметр или остался плейсхолдер `<...>`. Заполните `X`. |
| `config: subscriptions is empty` | Нет ни одной подписки в `config.yaml`. |
| `initial config: sing-box check failed ...` | Проблема не в узле, а в общих настройках (чаще всего неверные ключи Reality). Проверьте `reality.*`, читайте текст ошибки sing-box. |
| Ошибка подключения к БД при старте | Неверный пароль в `database_url` или спецсимволы в пароле. Пароль должен совпадать в `.env`, используйте только буквы и цифры. |
| `/healthz` отвечает 503 | sing-box не запущен или перезапускается. Смотрите строки `core:` в логе. |
| В `/status` пусто или узлов мало | Подписки не скачались (ищите строки `subs:` в логе, например `subs: host: 120 nodes` или `(fail #N)`, и алерт о подписке), либо узлы отброшены как неподдерживаемые. Проверьте подписку вручную: `curl -s -A sing-box URL \| head -c 500`. |
| Все узлы с `score: 0` сразу после старта | Нормально первые минуты: оценка появляется после первого цикла tier2 (~3 мин). |
| Все узлы с `score: 0` долго | Проверьте `net_down` в `/status`. Если `false`, а узлы мертвы, возможно, сервер не может добраться до `probe_urls` через узлы. Проверьте узел вручную (раздел ниже). Если `net_down: true`, проблема в сервере. |
| Клиент не подключается | Проверьте: порт 443 открыт (`ufw`, файрвол хостера), `public_host` правильный, ключи и `short_id` в ссылке совпадают с конфигом, пользователь не отключён (`bal users`), прошло 2-3 минуты после `adduser`. |
| В логе `REALITY: processed invalid connection`, клиент получает EOF | Шлюз не признал клиента как Reality-клиента и отдал ему «настоящий» сайт-маскировку. Проверьте: (1) ключи: `public_key` в ссылке должен быть парой к `private_key` в конфиге, `short_id` совпадает; после смены ключей нужны новые ссылки; (2) клиент поддерживает Reality и `flow=xtls-rprx-vision`; (3) сайт `handshake_server` поддерживает TLS 1.3 и X25519 с вашего сервера: `echo \| openssl s_client -connect www.microsoft.com:443 -servername www.microsoft.com -tls1_3 -groups X25519 2>&1 \| grep -E "Protocol\|Cipher"`; если сайт не отвечает или режется, выберите другой (проверенные кандидаты в разделе 11a). Быстро проверить связку ключей и сайт можно скриптом `smoke-test.sh` (предпроверка Reality). |
| Все узлы `allowed: false`, пользователи без интернета, алерт «Нет допустимых узлов» | Выход всех узлов в запрещённой стране или страна не определилась. Смотрите `exit_country` в `/status` и строки `geo:` в логе. Если страна не определяется, проверьте `geo_urls` (доступны ли они через узлы). Временно можно сузить `blocked_exit_countries` или поставить `exit_check: false`, но тогда пользователь может выйти в цензурируемой стране. |
| Узел из подписки есть, но в подписке пользователя его нет | Узел ещё не проверен, выход в запрещённой стране, или он не перекачивался после обновления версии (ссылка сохраняется при очередной загрузке подписок, до 30 минут). |
| Клиент подключился, но интернета нет | Смотрите в `/status`, есть ли `current: true` и `score > 0`. Если нет живых узлов, трафик отклоняется. Если узел текущий и живой, проблема у самого узла. |
| Частые переключения | Узлы нестабильны. Увеличьте `switch_confirm` или `switch_margin`. Посмотрите `SELECT * FROM switches ORDER BY ts DESC`. |
| Переключений нет, хотя есть лучший узел | Так и задумано: нужны margin 1,15 и 3 цикла подряд. |
| Соединения рвутся раз в несколько минут | Перезагрузки sing-box из-за изменения узлов в подписках или добавления пользователей. Проверьте в логе `core: config reloaded`. Если подписка часто меняет набор узлов, увеличьте `min_reload_interval`. |
| Алерт «подписка не обновляется» | Проверьте ссылку `curl` с сервера; провайдер мог заблокировать IP сервера или сменить токен. |
| Узел из подписки не появился | Формат не поддерживается (раздел 6.1) или sing-box его отверг (строка `rejected by sing-box check`). |

**Проверить узел вручную** (найдите `tag` в `/status`, логин проб `probe-<tag>`; пароль меняется при каждом
запуске и хранится только в памяти, поэтому проще смотреть результаты в `/status` и в таблице `checks`):

```sql
SELECT ts, tier, ok, latency_ms, target, error
FROM checks WHERE node_id = (SELECT id FROM nodes WHERE name = 'Имя узла')
ORDER BY ts DESC LIMIT 20;
```

Поле `error` покажет причину (таймаут, отказ соединения, ответ 4xx/5xx).

## 10. Безопасность

- **Порт 8080 без авторизации.** В `docker-compose.yml` он проброшен только на `127.0.0.1` сервера. Не меняйте
  на `0.0.0.0` и не открывайте в файрволе. Для удалённого доступа используйте SSH-туннель
  (`ssh -L 8080:127.0.0.1:8080 server`) или обратный прокси с паролем.
- **Секреты.** `.env` и `config.yaml` содержат пароль БД, приватный ключ Reality и токен Telegram. Права
  `chmod 600`, не кладите в git.
- **Токены подписок** в логи и алерты не попадают (в сообщениях остаётся только домен). Но они лежат в
  `config.yaml`.
- **Все пользователи выходят через один узел.** Трафик ваших пользователей видит оператор узла. Выбирайте
  подписки, которым доверяете.
- **Нет узлов значит нет доступа.** Если пул пуст или все узлы мертвы, трафик пользователей отклоняется, а не
  уходит напрямую с сервера, поэтому IP сервера не раскрывается.
- **Один публичный порт.** Снаружи открыт только 443 (Reality). База и Clash API недоступны извне.

## 11a. Сквозной тест на тестовом сервере

Скрипт `smoke-test.sh` поднимает систему целиком на одном сервере и проверяет её как настоящий пользователь.
Всё идёт через loopback, внешние порты не нужны. Требуется root, Docker с compose v2, python3, curl.

```bash
unzip vpn-balancer-fixed.zip && cd vpn-balancer
bash smoke-test.sh                  # на локальных тестовых узлах (около 8-10 минут, первая сборка образа дольше)
bash smoke-test.sh 'https://...'    # то же + в конце ваша реальная подписка (ещё 4-5 минут)
bash smoke-test.sh --cleanup        # удалить контейнеры, тома и временные файлы теста
```

Что делает скрипт: генерирует ключи Reality, поднимает PostgreSQL и балансировщик (отдельный
`docker-compose.smoke.yml`, host-сеть), три живых тестовых узла shadowsocks (роль VPN-провайдера) и один
мёртвый, локальную тестовую подписку. Затем создаёт пользователя и подключается к шлюзу настоящим клиентом
sing-box по VLESS+Reality.

| Что проверяется | Критерий |
|---|---|
| Reality без балансировщика (предпроверка) | отдельный сервер и клиент sing-box с теми же ключами проходят рукопожатие; перебираются сайты-маскировки (`www.microsoft.com`, `www.cloudflare.com`, `www.apple.com`, `dl.google.com`, `addons.mozilla.org`) и, при неудаче, отпечатки клиента; для каждого сайта проверяется TLS 1.3 с сервера; выбирается рабочий `handshake_server` |
| Сборка образа, `go vet`, путь к sing-box | образ собирается, `/usr/local/bin/sing-box` на месте |
| Подписка и пул | узлы загружены, мёртвый узел имеет оценку 0, один текущий |
| Метрики и БД | `/healthz`, `/metrics`, записи в `checks` и `switches` |
| Пользователь | `adduser`, `users`, клиентская ссылка рабочая |
| Реальный клиент | HTTP 204 через шлюз на двух сайтах |
| Failover | апстрим текущего узла остановлен: переключение на другой и восстановление трафика, время и число сбойных запросов в сводке |
| Возврат узла | поднятый узел снова получает оценку больше 0 |
| Смена подписки | новый узел появляется, sing-box перезагружается, клиент продолжает работать |
| Tier 3 | скорость измерена |
| Перезапуск контроллера | продолжает с того же узла, клиент работает |
| `deluser` | отключённый пользователь больше не проходит |
| `go test` | все 44 теста (юнит и интеграционные) проходят в контейнере |

Если предпроверка Reality не проходит ни с одним сайтом, это значит, что проблема не в балансировщике, а в
окружении сервера или в самом sing-box. Подробности пишутся в `logs/reality-diag.log` отчёта.

Результат: сводка PASS/FAIL/INFO на экране и архив `/root/smoke-report.tgz` (сводка, логи контроллера и клиента,
`/status`, метрики, статистика проверок и ошибок из БД, конфиг без приватного ключа). Пришлите его разработчику.
Код возврата скрипта 0, если нет ни одного FAIL.

Типичный результат на здоровом сервере: failover и восстановление трафика за 10-12 секунд (клиент за это время
получает несколько неудачных запросов, дальше всё работает), новый пользователь начинает проходить через
шлюз примерно через 30 секунд.

Если скрипт остановился на проверке портов: тест использует 443, 8080, 9090, 2080, 55432, 18080-18081,
18388, 18390, 18392. Освободите их или напишите, какие заменить.

## 12. Ограничения

- Все пользователи выходят через один общий лучший узел (исключения: правила `direct`/`block` из раздела 6b).
- Страна выхода определяется внешними сервисами (`geo_urls`) и точна настолько, насколько точны их базы. Узел, чей выход
  «плавает» между странами, определяется по самому осторожному ответу.
- Правила по IP срабатывают только если клиент подключается к IP, а не к имени сайта (раздел 6b).
- Подписка пользователя содержит ссылки на серверы провайдера: выдавайте её по HTTPS и только доверенным людям.
- Добавление пользователей и смена набора узлов перезагружают sing-box: соединения рвутся на пару секунд,
  не чаще раза в 2 минуты.
- Не разбираются Clash YAML, sing-box JSON, tuic, wireguard; отбрасываются транспорты xhttp/kcp/quic.
- `/status`, `/metrics`, `/healthz` без авторизации (слушайте только localhost); панель и `/api/*` требуют токена, но работают без TLS.
- Проверки мерят доступность и скорость с сервера, а не с устройства пользователя. Узел, хороший для сервера,
  может быть хуже для клиента в конкретной сети.
- Код проверен на локальных sing-box и PostgreSQL, но не на живых узлах провайдеров и не под нагрузкой
  сотен узлов. Первые дни следите за логами и `/status`.

## 13. Что присылать, если что-то не работает

1. Вывод `docker compose ps`.
2. Последние 200-300 строк `docker compose logs --tail 300 balancer` (токены подписок в логе скрыты, но
   проверьте на всякий случай).
3. Вывод `curl -s http://127.0.0.1:8080/status` (можно без имён узлов).
4. Что именно не работает: клиент не подключается, нет интернета, частые обрывы, что-то другое, и когда
   это началось.
5. Версия образа: `docker compose exec balancer sing-box version`.

Не присылайте: `.env`, `config.yaml` целиком, приватный ключ Reality, ссылки подписок и пользователей.
