## 1. Что это и как устроено

Пользователь подключается к **одному постоянному адресу** (ваш сервер, порт 443, VLESS+Reality). За ним
балансировщик держит пул узлов из ваших подписок, постоянно проверяет их и направляет трафик через лучший.
Пользователь не выбирает узел и не замечает переключений.

```
 клиент ──VLESS+Reality:443──►  ШЛЮЗ (контейнер gateway)                            узел 1 ─┐
 (один адрес)                   ├─ фронт: принимает TCP на 443                       узел 2 ─┼─► интернет
                                └─ sing-box (старый и новый экземпляр) ─selector────► ...    ─┘
                                        ▲
                                        │ API шлюза + Clash API (внутри сети compose)
                                 КОНТРОЛЛЕР (контейнер balancer)
                                 ├─ подписки (раз в 30 мин) ──► PostgreSQL
                                 ├─ проверки: tier1 / tier2 / tier3 / watchdog
                                 ├─ выбор лучшего узла, failover, правила, страны выхода
                                 └─ панель, команды, /status, /metrics, /healthz, Telegram
```

Компоненты:

| Компонент | Роль |
|---|---|
| **шлюз (`balancer gateway`)** | Маленький стабильный процесс: фронт на порту 443 и экземпляры sing-box. Принимает новые конфигурации от контроллера и включает их **без разрыва открытых соединений** (раздел 6d). Помнит последнюю конфигурацию и после своего перезапуска поднимает её сам. |
| **sing-box 1.11.4** | Внутри шлюза. Принимает пользователей (VLESS+Reality), содержит все узлы как outbound-ы и selector `proxy`. |
| **контроллер (Go)** | Скачивает подписки, генерирует конфиг sing-box, проверяет узлы, переключает selector, шлёт алерты, отдаёт панель и HTTP-статус. Его можно обновлять и перезапускать, пользователи этого не замечают. |
| **PostgreSQL 16** | Хранит пользователей, узлы, историю проверок и переключений. |

Режим `gateway: embedded` в config.yaml запускает шлюз внутри процесса контроллера (один контейнер, как в первых версиях;
тогда перезапуск контроллера обрывает соединения). Установщик и `docker-compose.yml` используют `gateway: external`.

Как проверяется конкретный узел: у sing-box есть служебный socks-вход (порт экземпляра, доступен только внутри сети контейнеров), у каждого узла
свой логин `probe-<tag>` с паролем, выведенным из ключа Reality. Запрос через логин `probe-X` всегда
уходит через узел X. Так контроллер измеряет именно этот узел, а не «текущий лучший».

Важная особенность: **все пользователи выходят через один общий лучший узел**. Это упрощает систему, но значит,
что нагрузка всех пользователей приходится на один апстрим.

## 2. Что нужно до начала

- Сервер с Linux, публичным IP (или доменом) и свободным портом **443/tcp**. Хватит 1 vCPU и 1 ГБ RAM для
  десятков пользователей и сотни узлов.
- Docker и Docker Compose v2 (`docker compose version`).
- Исходящий доступ сервера к: вашим подпискам, `gstatic.com`, `cloudflare.com`, `youtube.com`,
  `speed.cloudflare.com`, `ghcr.io` (один раз, для сборки образа), `proxy.golang.org` и `sum.golang.org`
  (при сборке образа).
- Одна или несколько ссылок подписок (base64 или список ссылок с `vless://`, `vmess://`, `trojan://`, `ss://`,
  `hysteria2://` / `hy2://`).
- Необязательно: Telegram-бот для алертов.

## 3. Установка шаг за шагом

### 3.0. Быстрая установка одним файлом (рекомендуется)

`install.sh` содержит весь проект внутри. На чистом Linux-сервере (Ubuntu/Debian, root, порты 443 и 8080 свободны):

```bash
sudo bash install.sh                                  # спросит адрес сервера и подписку
sudo bash install.sh -y --sub https://адрес-подписки  # без вопросов
```

Установщик: ставит Docker (если нет), генерирует ключи Reality и пароль БД, подбирает сайт-маскировку реальной проверкой
соединения, пишет `config.yaml` и `.env`, собирает и запускает систему, проверяет конфиг, создаёт пользователя `admin`
и печатает ссылку для клиента и токен панели. Подписку можно не указывать: `vpnb subs add АДРЕС` добавит её позже
(пока подписок нет, трафик пользователей отклоняется).

Параметры: `--dir` (по умолчанию `/opt/vpn-balancer`), `--host`, `--sub` (можно несколько), `--user`, `--port`, `--sub-server`
(выдача личных подписок на порту 8081), `--tg-token`/`--tg-chat`, `-y`.

После установки появляется команда `vpnb` (то же, что `balancer` внутри контейнера, раздел 6c): `vpnb status`, `vpnb nodes`, `vpnb adduser ИМЯ`, `vpnb token`.

| Действие | Команда |
|---|---|
| Обновить код (настройки, пользователи и данные сохраняются) | `sudo bash install.sh update` (новый install.sh) |
| Состояние | `sudo bash install.sh status` |
| Остановить | `sudo bash install.sh uninstall` |
| Удалить вместе с данными | `sudo bash install.sh uninstall --purge` |
| Только распаковать проект | `bash install.sh extract ПАПКА` |

Для сборки нужен доступ к ghcr.io, Docker Hub и proxy.golang.org. Дальше идёт ручная установка, если установщик не подходит.

### 3.1. Распаковать проект

```bash
unzip vpn-balancer-fixed.zip
cd vpn-balancer
```

### 3.2. Пароль базы данных

```bash
cp .env.example .env
```

В `.env` замените значение `DB_PASSWORD` на длинный случайный пароль. **Только буквы и цифры**, пароль
вставляется в URL подключения, спецсимволы (`@`, `/`, `:`, `#`) его ломают. Удобно так:

```bash
echo "DB_PASSWORD=$(openssl rand -hex 16)" > .env
```

### 3.3. Ключи Reality

```bash
docker run --rm --entrypoint sing-box ghcr.io/sagernet/sing-box:v1.11.4 generate reality-keypair
# PrivateKey: ....
# PublicKey:  ....
openssl rand -hex 8        # это short_id
```

Приватный ключ остаётся только на сервере. Публичный ключ и short_id попадают в ссылки пользователей.

### 3.4. Конфиг

```bash
cp config.example.yaml config.yaml
nano config.yaml
```

Обязательно заполните (значения в `<...>` система считает незаполненными и не запустится):

- `subscriptions`: ваши ссылки подписок.
- `public_host`: IP или домен сервера, куда будут подключаться клиенты.
- `reality.private_key`, `reality.public_key`, `reality.short_id`: из шага 3.3.
- В `database_url` пароль берётся из переменной `${DB_PASSWORD}`, менять ничего не нужно, если вы
  используете `docker-compose.yml` как есть.

Остальное можно оставить по умолчанию, описание всех параметров в [разделе 5](#5-справочник-по-configyaml).

`handshake_server` (по умолчанию `www.microsoft.com`) это настоящий HTTPS-сайт, под который
маскируется Reality. Выберите популярный сайт с TLS 1.3 и HTTP/2, не заблокированный у ваших пользователей.
Проверьте его с вашего сервера до запуска:
`echo | openssl s_client -connect САЙТ:443 -servername САЙТ -tls1_3 -groups X25519 2>&1 | grep -E "Protocol|Cipher"`
(должны быть TLSv1.3 и шифр, а не ошибка).

### 3.5. Запуск

```bash
docker compose up -d --build
docker compose logs -f balancer
```

Первая сборка скачивает Go-зависимости и образ sing-box. После старта в логах должны появиться строки вида
`subs: <домен>: N nodes` и `subs: refresh done, N nodes parsed`. Если запуск остановился сообщением `config: ... is not
set`, значит, остался незаполненный параметр.

### 3.6. Проверка, что всё работает

```bash
curl -s http://127.0.0.1:8080/healthz          # ok
curl -s http://127.0.0.1:8080/status | head -40
```

В `/status` у каждого узла есть `score`. Через 3-4 минуты после старта (первый цикл tier2) у живых узлов
он больше нуля, а один узел помечен `"current": true`. Порт 8080 слушает только `127.0.0.1` сервера, снаружи
он недоступен (и это правильно, см. [безопасность](#10-безопасность)).

### 3.7. Файрвол

Откройте только 443/tcp. 8080 наружу открывать не нужно.

```bash
# пример для ufw
ufw allow 443/tcp
```

## 4. Пользователи и подключение клиентов

Все команды выполняются внутри работающего контейнера:

```bash
alias bal='docker compose exec balancer balancer -c /etc/balancer/config.yaml'
```

| Команда | Что делает |
|---|---|
| `bal adduser alice` | Создаёт пользователя. Первая строка вывода: личная ссылка `vless://...` на балансировщик. Если включена выдача подписок (`sub_listen` и `sub_public_url`), второй строкой идёт адрес личной подписки |
| `bal users` | Список пользователей, их статус (`enabled`), ссылки на балансировщик и на подписку |
| `bal deluser alice` | Отключает пользователя (запись остаётся, `enabled=false`); его подписка тоже перестаёт открываться |
| `bal check` | Проверяет `config.yaml` (параметры, правила фильтра) без запуска чего-либо и без базы |

Ссылка одна на пользователя и постоянная. Она содержит адрес сервера, порт, UUID пользователя и параметры
Reality. Отправьте её пользователю. Повторно показать ссылку можно командой `bal users`.

**Когда пользователь начинает работать.** Контроллер сверяет список пользователей каждые 30 секунд. Изменение
состава пользователей приводит к перезагрузке sing-box, которая рвёт все текущие соединения на пару секунд.
Перезагрузки не чаще, чем раз в `min_reload_interval` (2 минуты), поэтому новый пользователь может появиться
с задержкой до 2-2,5 минут. Если добавляете нескольких, добавьте их подряд: они применятся одной перезагрузкой.

**Клиенты**, которые поддерживают VLESS+Reality с `xtls-rprx-vision`:

- Android: v2rayNG, Hiddify, NekoBox
- iOS / macOS: Streisand, Shadowrocket, Hiddify, V2Box
- Windows: v2rayN, Hiddify, NekoRay
- Linux: Hiddify, sing-box, v2rayN

Импорт: скопировать ссылку и в клиенте выбрать «Импорт из буфера обмена». Проверьте, что клиент не
добавляет собственный балансировщик или правила, которые ломают схему «один адрес».

Ссылка, которую выдаёт `adduser`, имеет вид:

```
vless://<uuid>@<public_host>:<inbound_port>?encryption=none&flow=xtls-rprx-vision&security=reality&sni=<handshake_server>&fp=<fingerprint>&pbk=<public_key>&sid=<short_id>&type=tcp#<имя>
```

Если вы меняете `public_host`, порт, ключи Reality или `short_id`, **все выданные ссылки перестают
работать**, пользователям нужно выдать новые (`bal users`).

### 4.1. Подписка для пользователя

Вместо одной ссылки пользователю можно выдать **личный адрес подписки**. В клиенте (Hiddify, v2rayN, Streisand,
Shadowrocket и другие) он добавляется как обычная подписка: клиент скачает список серверов и будет обновлять его сам.

Содержимое подписки:

1. **Первая строка: балансировщик**, личная ссылка пользователя (название берётся из `gateway_name`).
2. Дальше **все серверы, которые балансировщик загрузил из подписок**, но только те, чей выход проверен
   и находится не в запрещённой стране (раздел 6a). Название каждого начинается с измеренной страны выхода,
   например `[DE] Германия`. Узлы с неизвестным или запрещённым выходом и узлы, которых ещё не успели проверить,
   в подписку не попадают.

Как включить. В `config.yaml`:

```yaml
sub_listen: 0.0.0.0:8081                    # где слушать (пусто = выдача подписок выключена)
sub_public_url: https://vpn.example.com:8081 # как адрес выглядит снаружи, нужен для вывода adduser/users
sub_tls_cert: /etc/balancer/fullchain.pem   # необязательно: HTTPS без отдельного прокси
sub_tls_key: /etc/balancer/privkey.pem
gateway_name: Балансировщик
```

Откройте порт в файрволе и в `docker-compose.yml` (там есть закомментированная строка `8081:8081`). Адрес
подписки вида `https://vpn.example.com:8081/sub/<секрет>`, секрет у каждого пользователя свой.

Что важно знать:

- **Подписка содержит ссылки на серверы провайдера вместе с их ключами.** Тот, у кого есть адрес подписки,
  видит их. Выдавайте её только тем, кому доверяете, и обязательно по **HTTPS** (`sub_tls_*` или свой прокси):
  по обычному HTTP секрет и ссылки видны по пути. Без TLS в логе при старте будет предупреждение.
- Подписку нельзя угадать подбором: после 20 неверных запросов за 10 минут адрес получает ответ 429.
  Неверный секрет и отключённый пользователь дают одинаковый ответ 404.
- Чтобы увидеть содержимое глазами: добавьте `?raw=1` к адресу (выводится список без base64).
- Если пользователь обновляет подписку, он получает актуальный набор: узлы, чей выход перестал быть допустимым,
  из неё пропадают.
- Подписка выдаёт узлы с их собственным адресом, поэтому трафик через такой узел **не проходит проверку фильтра
  и страны выхода, которые делает балансировщик** для основной ссылки. Основной путь пользователя это первая строка.

## 5. Справочник по config.yaml

Длительности пишутся как `30s`, `5m`, `48h`. В значениях можно использовать переменные окружения
(`${DB_PASSWORD}`). Если задана переменная окружения `DATABASE_URL`, она перекрывает `database_url`.

### База и подписки

| Параметр | По умолчанию | Описание |
|---|---|---|
| `database_url` | нет | Строка подключения к PostgreSQL. |
| `subscriptions` | нет | Список URL подписок. Обязателен для запуска. |
| `sub_user_agent` | `sing-box` | User-Agent при скачивании подписок (некоторые провайдеры отдают разное содержимое разным клиентам). |
| `sub_refresh` | `30m` | Как часто обновлять подписки. |
| `node_identity` | `endpoint` | Как считать узлы. `endpoint`: ссылки с одинаковыми параметрами подключения (адрес, порт, UUID, ключи) сливаются в один узел, различающийся только названием. `link`: каждая ссылка подписки остаётся отдельным узлом, даже если параметры совпадают. Нужен, чтобы использовать **все** ссылки подписки и увидеть измеренную страну каждой. |
| `node_grace` | `48h` | Сколько узел остаётся в пуле после исчезновения из подписок. Защищает от кратковременных сбоев провайдера. |

### Вход для пользователей

| Параметр | По умолчанию | Описание |
|---|---|---|
| `public_host` | нет | Адрес сервера для ссылок пользователей. Обязателен. |
| `inbound_port` | `443` | Порт VLESS+Reality. Если меняете, поменяйте и проброс в `docker-compose.yml`. |
| `reality.private_key` | нет | Приватный ключ. Обязателен. |
| `reality.public_key` | нет | Публичный ключ (для ссылок). Обязателен. |
| `reality.short_id` | нет | 8 байт в hex. Обязателен. |
| `reality.handshake_server` | `www.microsoft.com` | Сайт для маскировки. |
| `reality.handshake_port` | `443` | Его порт. |
| `reality.fingerprint` | `firefox` | Отпечаток TLS в ссылках пользователей (по умолчанию `firefox`; раньше был `ios`). Если клиент не подключается и в логе шлюза `processed invalid connection`, верните `ios`. История: с `chrome` свежий Xray (v2rayNG) не подключался к шлюзу (в логе `processed invalid connection`), с `ios` заработало (проверено на реальном сервере). Вероятная причина: новые отпечатки Chrome/Firefox шлют постквантовое приветствие (X25519MLKEM768), которое sing-box 1.11 не распознаёт; поэтому `chrome`, `firefox`, `randomized` для таких клиентов не ставьте. Менять отпечаток достаточно в ссылке/профиле клиента. |

### sing-box и служебное

| Параметр | По умолчанию | Описание |
|---|---|---|
| `singbox_bin` | `sing-box` | Путь к бинарнику (в образе `/usr/local/bin/sing-box`, в PATH). |
| `work_dir` | `/var/lib/balancer` | Где хранится сгенерированный конфиг sing-box (том `balancer-data`). |
| `clash_api`, `test_port` | | Не используются с версии 5: порты экземпляров sing-box выбирает шлюз (`gateway_port_base`). Оставлены для совместимости конфигов. |
| `min_reload_interval` | `2m` | Минимальная пауза между включениями новой конфигурации (каждая запускает sing-box со всеми узлами). |
| `gateway` | `embedded` | `external`: шлюз в отдельном контейнере (рекомендуется, бесшовные обновления контроллера). |
| `gateway_url` | | При `external`: адрес шлюза для контроллера, `http://gateway:9000`. |
| `gateway_listen` | `0.0.0.0:9000` | Управляющий API шлюза (только внутри сети compose, защищён секретом). |
| `gateway_port_base` | `21000` | Начало диапазона внутренних портов экземпляров sing-box (по 10 портов на экземпляр, 4 экземпляра). |
| `gateway_secret` | из ключа Reality | Секрет API шлюза и Clash API. Обычно не задаётся: оба процесса выводят одинаковое значение из `reality.private_key`. |
| `drain_timeout` | `15m` | Сколько старой конфигурации разрешено обслуживать уже открытые соединения после переключения. |
| `drain_urgent` | `5s` | То же, если изменение что-то отзывает: пользователя, используемый сейчас узел, появилось правило `block` (раздел 6d). |
| `http_listen` | `127.0.0.1:8080` | Адрес HTTP-интерфейса статуса. В примере задан `0.0.0.0:8080` (внутри контейнера), наружу он проброшен только на `127.0.0.1` сервера. |

## 6. Как система выбирает узел

### 6.1. Подписки и пул узлов

- Каждые `sub_refresh` контроллер скачивает все подписки (3 попытки на каждую), разбирает ссылки и
  сохраняет узлы в БД.
- Формат подписки определяется автоматически: обычный список ссылок или base64 (любой вариант, в том числе
  с переносами строк).
- **ID узла** это sha1 от его канонического описания. Переименование узла в подписке его не меняет,
  история проверок сохраняется. Одинаковые узлы из разных подписок считаются одним.
- Узел, исчезнувший из подписок, остаётся в пуле ещё `node_grace`.
- Не поддерживаются и отбрасываются при разборе: Clash YAML, sing-box JSON, tuic, wireguard, транспорты
  xhttp / kcp / quic, TCP с HTTP-обфускацией, ss с plugin.
- Если `sing-box check` отвергает отдельный узел, он исключается из конфига и попадает в лог
  (`core: node XXXXXXXXXX rejected by sing-box check, excluded: ...`). Остальные узлы работают.

### 6.2. Четыре вида проверок

| Проверка | Интервал | Что делает |
|---|---|---|
| **Tier 1** | 1 мин | TCP-подключение к каждому узлу. UDP-протоколы (hysteria2) пропускаются. |
| **Tier 2** | 3 мин | HTTPS-запросы через узел к каждому из `probe_urls`. Узел рабочий, если ответило большинство. Измеряется задержка. |
| **Tier 3** | 45 мин | Скачивание 5 МБ через топ-5 узлов, измерение скорости. |
| **Watchdog** | 5 с | Проверка текущего узла. Два сбоя подряд дают немедленный failover и сброс соединений. |

### 6.3. Оценка узла

```
score = 100 × успешность
        − min(задержка_ewma / 10, 40)
        − min(джиттер / 20, 10)
        + бонус_скорости (до +10, достигается на 40 Мбит/с)
```

Оценка равна **0**, если успешность в окне последних проверок ниже 0,6 или было 2 сбоя подряд.

### 6.4. Когда происходит переключение

- **Срочно (failover):** текущий узел получил оценку 0, то есть упал. Переключение сразу на лучший из живых,
  активные соединения сбрасываются, чтобы клиенты переподключились заново.
- **Плановое улучшение:** другой узел должен быть лучше текущего минимум в `switch_margin` (1,15) раза
  **`switch_confirm` (3) цикла tier2 подряд**. Если преимущество пропало хотя бы в одном цикле, счётчик
  обнуляется. Это защищает от «дёргания» между похожими узлами.
- При равных оценках побеждает узел с меньшей задержкой, затем по ID (выбор детерминирован).

### 6.5. Карантин

Узел, провалившийся 3 раза подряд, уходит в карантин: 1, 2, 4, 8, 16, затем максимум 30 минут. Во время
карантина он не проверяется. Один успешный tier2 снимает карантин.

### 6.6. Защита от ложных тревог

- **Базовая связность.** Перед записью результатов проверяется TCP до `baseline_addrs`. Если у самого
  сервера нет интернета, результаты отбрасываются, узлы не наказываются, переключений нет, приходит алерт.
- **Перезагрузка sing-box.** Проверки, которые шли во время перезагрузки, отбрасываются. Watchdog
  первые 5 секунд после перезагрузки сбои не считает.
- **Непроверенные узлы.** Алерт «все узлы недоступны» не срабатывает, пока узлы ни разу не проверялись.

### 6.7. Что видит пользователь при failover

Соединения сбрасываются, клиент переподключается к тому же адресу, трафик идёт уже через новый узел. Обычно это
пауза в несколько секунд, страницы и видео продолжают работать после повторного запроса. Долгие загрузки и
стримы могут оборваться.

### 6.8. Перезапуск системы

При старте контроллер продолжает с последнего выбранного узла (из таблицы `switches`). Если узлы уже есть в
БД, система поднимается сразу, не дожидаясь скачивания подписок. Если БД пуста (первый запуск), сначала
скачиваются подписки.

## 6a. Страна выхода узла

Узел в подписке часто только «прокладка» (вход в России, дальше цепочка). Название в подписке ничего не
гарантирует: метка «США» может вести на выход в России. Поэтому балансировщик **сам измеряет**, откуда узел
выходит в интернет:

1. После успешной проверки узла (tier 2) он отправляет через этот узел запросы к сервисам из `geo_urls`
   (по умолчанию ipinfo.io, api.country.is, ifconfig.co). Сервис видит адрес **последнего узла цепочки** и называет его страну.
   Берутся два ответа; если хоть один указывает страну из запрещённого списка, узел считается находящимся в ней
   (выбирается безопасная сторона).
2. Результат записывается в базу (`nodes.exit_country`, `nodes.exit_ip`) и повторяется раз в `geo_ttl` (6 часов).
3. Если выход в стране из `blocked_exit_countries`, **узел исключается**: он не попадает в выбор для пользователей
   (в sing-box он вообще не входит в `proxy`), не выдаётся в подписке, и приходит Telegram-алерт.
4. Пока страна **неизвестна** (ещё не измерена, сервисы не ответили), узел тоже не используется. Это намеренно:
   лучше подождать минуту после старта, чем отправить человека в цензурируемую страну.
5. Узел из запрещённой страны **не выбрасывается совсем**, а уходит в «карантин» по стране (в `/status` он помечен
   `quarantined: true`, `allowed: false`): проверки продолжаются, страна измеряется заново через `geo_blocked_ttl`
   (30 минут), и если выход изменился на допустимый, узел возвращается в работу.
6. Если **текущий** узел при проверке оказался в запрещённой стране, контроллер переключает пользователей на лучший допустимый.

**Все ссылки подписки как отдельные узлы.** По умолчанию ссылки с совершенно одинаковыми параметрами подключения
считаются одним узлом (для сервера это одно и то же соединение, проверять 26 копий смысла нет). Если нужно использовать
каждую ссылку подписки отдельно (например, провайдер выдаёт 100+ ссылок и вы хотите видеть и использовать каждую),
включите `node_identity: link`: тогда каждая ссылка станет узлом со своей оценкой, своим измерением страны и своей
строкой в пользовательской подписке, а узлы с выходом в запрещённых странах отфильтруются автоматически.
Если несколько ссылок ведут на одну и ту же машину, они покажут одинаковую страну и одинаковую задержку.

Если у всех узлов выход запрещён или неизвестен, трафик пользователей **отклоняется**, а не идёт напрямую
через сервер. Это то самое «ни в коем случае не подключать пользователя через себя»: сервер находится в России, и его
собственный выход не должен становиться запасным вариантом. Приходит алерт «Нет допустимых узлов».

Посмотреть результат: `curl -s 127.0.0.1:8080/status | jq '.nodes[] | {name, exit_country, exit_ip, allowed}'`.
Поле `allowed` значит «может нести трафик пользователей». Метрика `balancer_nodes_excluded_by_country`.

**Как проверить сервис в целом**, если вы не доверяете названиям в подписке: сравните `name` и `exit_country`
в `/status`. Одинаковые ссылки с разными названиями (в тестовой подписке 108 ссылок вели на 5 серверов) сливаются
в один узел, потому что для сервера это одно и то же соединение. В `/status` вы увидите реальное число серверов.

**Не определяется страна?** Сервисы из `geo_urls` должны быть доступны **через узлы**. Если провайдер блокирует часть
из них, добавьте свой сервис, который отдаёт JSON с полем `country` или двухбуквенный код. В логе при определении
пишется `geo: <узел> exits in DE (1.2.3.4)`.

## 6b. Правила фильтра: что пускать напрямую, что блокировать

По умолчанию **весь трафик пользователя идёт через балансировщик**. Исключения задаются списком `rules` в
`config.yaml`. Правила применяются только к трафику пользователей (не к проверкам узлов) и вычисляются сверху вниз,
**срабатывает первое подошедшее**. Поэтому конкретные правила ставьте выше общих.

```yaml
rules:
  - action: proxy           # исключение из правила ниже: этот поддомен идёт через балансировщик
    match:
      - "*.gov.ru"
  - action: direct          # идти напрямую через сервер (он в России: полезно для российских сайтов)
    match:
      - "*.ru"              # любой домен в зоне .ru
      - "*.xn--p1ai"        # зона .рф (в punycode)
      - "sberbank.com"      # ровно этот домен
      - "10.20.0.0/16"      # сеть
      - "100.200.255.7"     # один адрес
  - action: block           # отклонить
    match:
      - "keyword:tracker"   # в имени есть слово
      - "port:25"           # SMTP
      - "port:6881-6999"    # торренты
default_action: proxy       # остальное: через балансировщик
```

Порядок важен: `*.gov.ru` стоит выше `*.ru`, иначе до него дело не дойдёт.

Действия: `direct` (напрямую с сервера), `block` (отклонить соединение), `proxy` (через балансировщик).

**Что можно писать в `match`:**

| Запись | Значение |
|---|---|
| `*.ru` | любой домен зоны `ru` (и сам `ru`) |
| `*.example.com`, `.example.com` | `example.com` и все его поддомены |
| `example.com` | только этот домен |
| `ads*.example.com`, `?` | подстановка внутри имени (превращается в регулярное выражение) |
| `100.200.255.0/24`, `2001:db8::/32` | сеть (IPv4 и IPv6) |
| `1.2.3.4` | один адрес |
| `port:25`, `port:6881-6999` | порт или диапазон портов |
| `keyword:слово` | в домене есть это слово |
| `regex:^a.+b$` | регулярное выражение по домену |
| `domain:`, `suffix:`, `cidr:` | явная форма, если сомневаетесь |

Правила проверяются при запуске: опечатка в правиле останавливает запуск с понятным сообщением (проверить
заранее: `bal check`). Изменение правил применяется после перезапуска контроллера.

**Ограничения:**

- Правила по IP-адресам и сетям (`100.200.255.0/24`) срабатывают, **когда клиент сам подключается к IP-адресу**.
  Если клиент отправляет имя сайта, сервер его не переводит в IP для сравнения (это сделало бы запрос DNS с сервера в России
  и могло бы дать подмену). Для сайтов пишите правила по доменам.
- Домены с не-ASCII символами пишите в punycode (`xn--p1ai` вместо `рф`).
- Правило `direct` отправляет трафик с **IP-адреса сервера**: он российский, и со стороны сайтов это российский пользователь.
  Использовать для российских сервисов удобно, для остального нет.
- Если допустимых узлов нет, правила `proxy` превращаются в `block`, а `direct` и `block` продолжают работать как задано.
- `default_action: block` включает режим белого списка: пропускается только то, что разрешено правилами
  (`direct`/`proxy`), остальное отклоняется.

## 6c. Веб-панель, консольные команды и настройки на лету

Всем, что нужно для работы, можно управлять двумя способами: веб-панелью и командами. Оба работают с одним и тем же API
контроллера и одними и теми же настройками.

### Веб-панель

Панель встроена в бинарник (`ui.html`), отдельно ничего ставить не нужно. Она слушает на `http_listen` (по умолчанию
`127.0.0.1:8080` на сервере), наружу не проброшена. Открывать через SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 root@СЕРВЕР      # затем в браузере http://127.0.0.1:8080/
docker compose exec balancer balancer -c /etc/balancer/config.yaml token    # токен для входа
```

Токен создаётся при первом запуске и хранится в базе (таблица `settings`, ключ `admin_token`). Без него видны только `/status`,
`/metrics`, `/healthz` (как раньше), всё, что показывает секреты или что-то меняет, требует токена.

Панель чёрная, с острыми углами. Левое меню делится на две части. **Сервис** (обычные цвета): всё, что связано с людьми. **Администратор** (бледно-красный цвет заголовков, рамок и кнопок): то, что относится к вашему собственному балансировщику и машине. Адрес вкладки сохраняется в строке браузера (`#users/people/имя`), поэтому её можно открыть по ссылке и обновить страницу без потери места.

Вкладки части «Сервис»:
- **Обзор**: сколько людей, активных, у кого кончается срок, заблокированных, платежи на подтверждение; балансировщики канала пользователей; трафик всей сети; сводка по каналу админов.
- **Пользователи**: всё, что связано с людьми, в одном месте. Подвкладки: «Люди», «Тарифы», «Платежи», «Промокоды», «Рефералы», «Бот и оплата». Список людей слева (поиск, фильтры по каналу и статусу, сортировка), выбранный человек открывается **справа** на большом экране; на узком экране карточка открывается на отдельном экране с кнопкой «К списку», а кнопка «вкладка» открывает её в отдельной вкладке браузера. Карточка: «Сводка» (статус, срок, трафик, ник и канал), «Доступ» (какие группы серверов получает), «Статистика», «Аккаунт» (почта, баланс, Telegram, пополнение, смена пароля), «Ссылки» (подписка, балансировщики, QR). Блокировка и срок меняются из карточки.
- **Канал пользователей**: второй балансировщик в отдельной вкладке. Свои серверы: подписку провайдера (`https://…`) или отдельный сервер ссылкой (`vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://`) можно добавить прямо здесь, это настройка `users_subscriptions`. Показаны его три режима (текущий, лучшая скорость, лучший пинг), узлы пула, люди канала и то, в какой канал попадают новые люди с сайта. Пока пул пуст, канал работает на узлах админов.
- **Серверы**: «Группы» (наборы серверов, которые выдаются тарифу или человеку: слева список, справа редактор с добавлением и удалением серверов и подписок группы, видно, кто группу получает), «Серверы по ссылке», «Внешние подписки», «Установленные серверы» (сеть, раздел 6g).
- **Сайт**: домен, сертификат, оформление, форум; подвкладки «Инструкции» и «Форум».

Вкладки части «Администратор»:
- **Узлы админов**: таблица узлов с оценкой, задержкой, страной выхода, статусом, поиск и фильтры, кнопка «закрепить».
- **Клиенты**, **Сервер**, **Консоль**, **WireGuard**, **Бэкапы**: как описано в разделах 6e и 6f.
- **Настройки**: «Основные» (страны выхода, правила фильтра, подписки админов, переключение, качество узлов, режим «по трафику», название) и «Все параметры»: каждый параметр, который можно менять без перезапуска, с описанием, поиском, кнопками «Сохранить» и «Сбросить».
- **Терминал**: строка команд прямо в панели. Выполняет те же команды, что и командная строка сервера (таблица ниже), справа справочник со всеми командами и настройками с описаниями; клик по подсказке вставляет её в строку, стрелки вверх и вниз листают историю, `clear` очищает экран. `help` печатает список, `help КОМАНДА` или `help КЛЮЧ` описывает одну команду или настройку. Команды `run` и `token` в терминале панели отключены.

Панель не использует внешних скриптов и шрифтов, не вставляет данные как HTML, ставит `Content-Security-Policy`.

### Настройки на лету

Эти ключи хранятся в базе и **перекрывают config.yaml**; контроллер подхватывает изменения не позже чем через 10 секунд, перезапуск не нужен:

Полный список (около 50 ключей) показывают вкладка «Настройки → Все параметры», команда `help settings` и справочник терминала: подписки обоих каналов, страны, правила, переключение, качество и скорость узлов, сайт, оплата и рефералы, бот, резервные копии, частоты и тайминги проверок.

Остальное (порты, ключи Reality, пути, БД) меняется только в config.yaml с перезапуском. Изменение правил, стран или набора узлов приводит к перезагрузке sing-box (не чаще `min_reload_interval`, кроме первого допустимого узла). `reset КЛЮЧ` убирает значение из базы: действующее значение сменится на config.yaml после перезапуска контроллера. ```bash

```bash
balancer countries block FR              # ещё одна запрещённая страна
balancer rules add block port:25         # запретить SMTP
balancer set switch_margin 1.5
balancer nodes --country DE
```

## 6d. Бесшовные обновления и смена конфигурации

Цель: пользователь не замечает ни обновления программы, ни смены узлов, ни добавления пользователей.

**Как это устроено.** Перед sing-box стоит TCP-фронт. Новая конфигурация никогда не заменяет работающий sing-box:
рядом запускается второй экземпляр с новой конфигурацией, фронт отправляет в него все **новые** подключения, а
открытые продолжают работать на старом экземпляре, пока не закончатся (но не дольше `drain_timeout`, по умолчанию 15 минут). Когда
старый экземпляр опустеет, он останавливается. Если новая конфигурация не запустилась (ошибка проверки sing-box), остаётся работать старая.
Одновременно живут до четырёх экземпляров.

| Событие | Что видит пользователь |
|---|---|
| Новые узлы в подписке, узел вернулся или пропал (не текущий) | ничего: открытые соединения доживают, новые идут на свежую конфигурацию |
| Добавлен пользователь, добавлено правило `direct`/`proxy` | ничего |
| Обновление контроллера (`install.sh update`) | ничего: шлюз работает без него; проверки приостановлены на 5-10 с. Новый контроллер видит, что шлюз уже работает с нужной конфигурацией, и ничего не переключает |
| Смена узла (failover, «узел лучше») | как раньше: failover обрывает соединения, чтобы клиенты сразу ушли на живой узел |
| **Отзыв**: пользователь отключён, текущий узел ушёл в запрещённую страну, добавлено правило `block`, `default_action: block` | открытые соединения обрываются через `drain_urgent` (5 с): запрет должен действовать сразу |
| Перезапуск шлюза (`update --gateway`, перезагрузка сервера) | обрыв на 2-5 с; шлюз сам поднимает последнюю конфигурацию, не дожидаясь контроллера |
| Падение sing-box | шлюз перезапускает его сам, соединения этого экземпляра обрываются |

Состояние видно в `vpnb status` (строка «шлюз»: сколько подключений на новой конфигурации и сколько ещё доживает на старой),
в панели (карточка «Шлюз») и в `GET /api/overview`.

**Что бесшовно нельзя.** Перезапуск самого шлюза (новая версия sing-box или кода шлюза) обрывает соединения на несколько
секунд. Установщик делает это только по `update --gateway`. Источник клиентского адреса sing-box теперь видит как 127.0.0.1 (фронт
пересылает TCP); правила по адресу клиента не используются.

## 6e. Статистика сервера и клиентов, консоль

Панель (вкладки «Сервер», «Клиенты», «Консоль»), команды `stats` и `logs` и HTTP API (`/api/stats`, `/api/stats/history`, `/api/logs`) показывают одно и то же.

### Сервер
Каждые 5 секунд контроллер измеряет процессор, память, диск, нагрузку (load average) и трафик шлюза. Графики берут точки раз в 10 секунд за последние 24 часа из памяти; раз в 30 секунд точка сохраняется в базу (таблица `metrics`, хранится 14 дней), поэтому после перезапуска графики не пустые, а период «7 дней» строится по базе.
- Процессор, память, нагрузка, время работы относятся ко всему серверу (внутри контейнера эти данные общие с хозяином). Диск это файловая система, на которой лежит Docker.
- «Сеть клиентов» это байты, прошедшие через шлюз от пользователей (вверх) и к ним (вниз), без трафика проверок узлов. Это не счётчик сетевой карты сервера: он был бы почти вдвое больше, так как включает и трафик до узлов подписки.

### Клиенты
Шлюз считает байты каждого подключения у входа (на 443) и определяет пользователя по строке `[имя] inbound connection` из лога sing-box (для этого шлюз запускает sing-box с уровнем логов `info`, а в консоль пропускает только предупреждения и ошибки). Сумма по пользователям записывается в базу по часам (таблица `traffic_hourly`, хранится 180 дней), время последней активности и адрес в `user_seen`.
- **Онлайн**: есть открытое соединение. **Передаёт**: в последние ~10 секунд шли данные. Скорость «сейчас» это байты за последний интервал в 5 секунд.
- «24 часа», «7 дней», «30 дней» это скользящие окна от текущего момента, а не календарные сутки (так не зависит от часового пояса сервера).
- «Скачал ↓» означает данные к клиенту, «Отправил ↑» от клиента. Учитывается объём внешнего слоя (с заголовками Reality/TLS), на несколько процентов больше полезных данных.
- Блок «Не опознанные подключения»: подключения, не прошедшие проверку Reality (неверные ключи, short id или отпечаток в клиенте, сканеры из интернета), и подключения, оборвавшиеся до определения пользователя. Для каждого адреса видно число попыток. В консоль такие подключения не пишутся по строке на каждое: раз в 30 секунд выводится одна сводная строка.
- Удалённые из базы пользователи остаются в таблице трафика с пометкой «удалён». Отключённый пользователь показывается как «отключён».

**Приватность.** Хранятся только имя пользователя, адрес клиента, время и объём. Какие сайты открывают пользователи, не сохраняется, не показывается и не попадает в консоль (строки об обычных соединениях sing-box отбрасываются сразу при чтении).

### Консоль
Последние 3000 строк: контроллера (проверки, подписки, переключения, ошибки) и шлюза (запуск, смена конфигураций, предупреждения и ошибки sing-box). Страница обновляется раз в 2 секунды, строки можно фильтровать по тексту и скачать. Постоянные логи остаются там же, где и раньше: `docker compose logs`.

### Обновление
Статистика шлюза появилась в новой версии шлюза. Если контроллер новее шлюза, вкладки показывают «шлюз старой версии»: выполните `bash install.sh update --gateway` (обрыв соединений 2-5 секунд).

## 6f. WireGuard: домашняя сеть через балансировщик

Балансировщик принимает WireGuard-туннель от роутера (MikroTik и любого другого с WG). Устройства за роутером выходят в интернет
через тот же выбор узлов, те же правила фильтра и ту же политику стран, что и обычные клиенты. Настраивать на самих устройствах ничего не нужно.

**Как это устроено.** Устройство → роутер → WireGuard (UDP, `wg_port`, по умолчанию 51820) → отдельный процесс sing-box в шлюзе
(он не входит в кольцо blue/green и не перезапускается при обновлениях конфигурации) → SOCKS с UDP-over-TCP на активный экземпляр
шлюза → выбранный узел. Трафик каждого пира учитывается под именем `wg-<имя>` (вкладка «Клиенты», метка «WireGuard»).
Доменные правила фильтра работают и для WG: трафик определяется по SNI/HTTP-заголовку (sniff).
Если подходящих узлов нет (все страны запрещены и т.п.), трафик пира режется, напрямую он не уходит.

**Шаги.**
1. Откройте UDP-порт на сервере (установщик делает `ufw allow 51820/udp` и публикует порт в compose). Если сервер стоит дома за роутером,
   пробросьте UDP 51820 на сервер или подключайте роутер к его локальному адресу.
2. Вкладка «WireGuard» → создайте пир: имя и подсеть(и), которые будут идти через VPN (по умолчанию 192.168.50.0/24).
   То же в консоли: `vpnb wg add office 192.168.50.0/24`, `vpnb wg list`, `vpnb wg show office`, `vpnb wg on|off|del office`.
3. Нажмите «Скрипт MikroTik», укажите адрес сервера (endpoint) и вставьте скрипт в терминал RouterOS 7. Он создаёт WG-интерфейс, пир,
   мост `br-vpn` с DHCP для отдельной подсети, таблицу маршрутизации `vpn`, правило `lookup-only-in-table` (kill switch: при падении
   туннеля устройства подсети остаются без интернета, а не уходят в обход) и MSS clamp. MTU туннеля 1380.
4. Переключение: проводное или Wi-Fi устройство «под VPN» = порт или SSID в мосте `br-vpn`; «без VPN» = обычный мост. Вариант на уровне
   отдельных устройств без смены подсети: address-list + mangle `mark-routing` (закомментированный блок в скрипте).
5. Для приложения WireGuard (телефон, ноутбук) есть кнопка «Профиль WireGuard» (`?format=wgquick`).

**Замечания.**
- Скрипт RouterOS - шаблон, на реальном железе не проверялся: сверьте имена интерфейсов и пулов с вашей конфигурацией.
- DNS: роутер раздаёт 1.1.1.1 и 8.8.8.8, запросы идут внутри туннеля. Если ваш роутер перехватывает DNS, проверьте, что для подсети VPN это не так.
- При добавлении, удалении или отключении пира WG-процесс перезапускается (пауза в туннеле 1-2 с); смена выбора узлов туннель не обрывает.
- Обновлять шлюз нужно командой `update --gateway` (в нём появился WG-процесс), иначе контроллер напишет, что шлюз старый.
- Настройки: `wg_port`, `wg_network` (IPv4, от /16 до /29), `wg_endpoint`. API: `/api/wg`.

## 6g. Режимы балансировщика, две подписки и QR-коды

У каждого пользователя три ключа на одном порту шлюза, и каждому соответствует свой выбор узла:

| Режим | Ссылка | Как выбирается узел |
|---|---|---|
| текущий | `<имя>` | прежняя логика: лучший по оценке с гистерезисом |
| лучшая скорость | `<имя> · лучшая скорость` | из группы лучших по оценке (с учётом правил качества и обязательных сервисов) узел с наибольшей свежей скоростью |
| лучший пинг | `<имя> · лучший пинг` | из той же группы узел с наименьшей задержкой |

Группа лучших: до 25% живых допущенных узлов, но не меньше 5 и не больше 15. Мёртвый узел или узел из запрещённой страны в группу не попадает. Режим меняет узел, только если новый
заметно лучше несколько циклов проверки подряд: по скорости в 1,3 раза и не меньше чем на 2 Мбит/с, по пингу на 25% и не меньше чем на 15 мс; число циклов то же, что и для основного
балансировщика (`switch_confirm`). Если узел режима отказал или перестал подходить по качеству, он заменяется сразу. Фильтр правил и политика стран одинаковы для всех трёх режимов.
Трафик и сессии учитываются на самого пользователя, режим виден в сессии. Ключи режимов выводятся из ключа пользователя, удаление пользователя убирает все три.
Узлы, на которых сейчас работают режимы, помечены в таблице «Узлы», три карточки есть на «Обзоре». В имени пользователя нельзя символ `~`.

Подписки (адрес `sub_public_url`, в панели у каждого пользователя):
- `/sub/<токен>/balancers`: только три балансировщика;
- `/sub/<токен>` (то же `/sub/<токен>/all`): три балансировщика и все допущенные серверы.

В панели у каждой из пяти ссылок (три балансировщика, две подписки) есть кнопки «Копировать» и «QR». QR строится на сервере (`/api/qr`, нужен токен панели). Команды `vpnb users`, `vpnb sub ИМЯ`
и `adduser` тоже печатают все ссылки.

**Отпечаток TLS.** По умолчанию теперь `firefox` (`reality.fingerprint`). Клиентам нужно обновить подписку. Если клиент перестал подключаться и в логе шлюза `processed invalid connection`, верните `ios`.

## 6h. Сайт для пользователей: домен, сертификат, регистрация, оплата (итерация 12)

Публичный сайт встроен в контроллер (тот же PostgreSQL). Включается и настраивается в панели, вкладка **«Сайт»**; перезапуск не нужен.

**Что видит пользователь.** Главная страница, регистрация (почта + пароль, без подтверждения почты), вход, личный кабинет: срок подписки («осталось N дней», дата окончания), использованный трафик (всего, ↑/↓, подключений), ссылки на подписки (балансировщики; балансировщики + все серверы), QR-коды, смена пароля, страница оплаты и список платежей. При регистрации создаётся VPN-пользователь с именем, равным почте, и пробный период `site_trial_days` (3 дня; 0 = без пробного).

**Что делает администратор (вкладка «Сайт»).** Включить/выключить сайт, домен, почту для Let's Encrypt, название, контакты поддержки, открытая/закрытая регистрация, пробные дни, режим оплаты; состояние сертификата (домен, срок, издатель, ошибка) и кнопка «Проверить сейчас»; тарифы (название, дни, цена, валюта, включён); аккаунты (создать с временным паролем, +дни, дата окончания, без срока, блокировка, сброс пароля, удаление вместе с VPN-пользователем); заявки на оплату (подтвердить / отменить). Срок можно менять и во вкладке «Клиенты» у любого пользователя (`POST /api/users/ИМЯ/expiry`). Просроченный ключ исчезает из шлюза в течение 30 секунд и перестаёт отдавать подписку; продление возвращает его.

**Сертификат.** Автоматически, Let's Encrypt (`golang.org/x/crypto/acme/autocert`), проверка HTTP-01 на порту 80 (или TLS-ALPN на HTTPS-порту сайта). Сертификат и ключ хранятся в таблице `acme_cache` PostgreSQL, продлевается сам. Настройка `site_acme_staging` включает тестовый центр (сертификат не доверен браузерами, зато нет лимитов; полезно для первой проверки DNS и портов; отдельный кэш `staging/`).

Порядок включения:
1. A/AAAA-запись домена указывает на IP сервера.
2. Порты 80 и 8443 открыты (установщик публикует их в compose и открывает в ufw; если порт 80 занят, он предупредит).
3. Панель → «Сайт»: домен, почта, переключатель «включить». Через минуту-две статус сертификата станет «выдан». При ошибке в статусе указана причина и подсказка (DNS, порты).
4. Сайт открывается по `https://домен:8443`.

**Сайт на обычном 443.** Порт 443 занят шлюзом Reality. Настройка `site_via_reality` переводит маскировку шлюза на сам сайт: браузеры и сканеры, пришедшие на 443 с SNI вашего домена, получают настоящий сайт с настоящим сертификатом, а клиенты с ключом - VPN. Включается автоматически только когда сертификат уже выдан и проверен (`site_dest`, по умолчанию `balancer:8443`); при проблеме шлюз возвращается к прежней маскировке. Ссылки подписок при этом используют домен как SNI, поэтому клиентам нужно обновить подписку. Сайт тогда открывается по `https://домен` без порта.

**Оплата - заглушка.** Интерфейс `PaymentProvider`; режимы `site_payment`: `manual` (по умолчанию: заявка ждёт, администратор подтверждает во вкладке «Сайт» - срок продлевается от max(конец, сейчас), платёж подтверждается один раз), `stub_auto` (ТЕСТ: оплата проходит сразу без денег; любой пользователь продлевает себя бесплатно, не оставляйте на боевом сервере), `off` (оплата выключена). Реальную платёжную систему подключают, реализовав `PaymentProvider` (создание платежа, возврат на страницу, вебхук с проверкой подписи, вызов `MarkPaid`).

**Безопасность сайта.** Пароли - bcrypt; сессия в cookie `vsid` (HttpOnly, SameSite=Lax, Secure на HTTPS), в БД хранится хэш токена; CSRF-токен на каждую форму + проверка Origin/Referer; ограничения частоты (вход по IP и по почте, регистрация по IP, платежи по аккаунту); CSP с nonce; HSTS; вход не выдаёт, существует ли почта. Заблокированный аккаунт теряет сессии и VPN-ключ.

**Настройки** (`vpnb set`/панель): `site_enabled`, `site_domain`, `site_email`, `site_name`, `site_support`, `site_registration`, `site_trial_days`, `site_payment`, `site_acme_staging`, `site_via_reality`. Только в config.yaml: `site_http_listen` (`:80`), `site_https_listen` (`:8443`), `site_allow_http` (сайт по HTTP без домена, пароли не шифруются - только для проверки), `site_dest`.

**API (токен администратора):** `GET /api/site`, `POST /api/site/cert/check`, `GET/POST /api/plans`, `PUT/DELETE /api/plans/{id}`, `GET/POST /api/accounts`, `POST /api/accounts/{id}/{block|unblock|delete|reset-password|expiry}`, `GET /api/payments`, `POST /api/payments/{id}/{confirm|cancel}`, `POST /api/users/{имя}/expiry` (тело: `extend_days` | `until` YYYY-MM-DD | `unlimited`).

**Ограничения.** Почта не подтверждается и письма не отправляются: сброс пароля делает администратор. Настоящего приёма денег нет. Реальный выпуск сертификата на реальном домене не проверялся в тестовой среде (там нет доступа к Let's Encrypt): логика проверена на самоподписанном сертификате.

## 6i. Домен вместо IP, свои узлы и сборки, подписки по пользователям и тарифам, статистика (итерация 13)

**Всё строится на домене.** В config.yaml задаётся `domain:` (основной: `nvrk.ytc-srv.org`). Из него берутся адрес в ссылках на балансировщик, адреса подписок, домен сайта и сертификата, адрес WireGuard-сервера для роутера. Голые IP в ссылки не попадают. Запись A домена должна указывать на сервер. Установщик спрашивает домен (`--domain`, по умолчанию nvrk.ytc-srv.org), проверяет DNS и предупреждает, если домен указывает не на этот сервер. При обновлении старой установки он дописывает `domain:` в config.yaml (берёт имя из `public_host`, если там домен, иначе nvrk.ytc-srv.org). Клиентам после смены адреса нужно обновить подписку. `public_host` оставлен для совместимости; если в нём IP, в логе будет предупреждение.

**Свои узлы.** Вкладка «Подписки» → «Свои узлы»: добавляется ссылка узла (vless, vmess, trojan, ss, hysteria2). Такие узлы не входят в балансировщик, не проверяются и не принимают трафик пользователей. Ссылка хранится в базе и не показывается ни в панели, ни через API, ни пользователям: в панели видны название, тип и адрес узла, заменить ссылку можно только вставив новую. Пользователь получает свои узлы только внутри подписок.

**Сборки.** Сборка — набор своих узлов с названием и адресом (`vip`, `games`). Она отдаётся подпиской `https://домен/sub/<токен>/b/<адрес>`. Адрес сборки после создания не меняется (он записан в списках пользователей и тарифов). Удаление сборки убирает её из личных списков, тарифов и списка по умолчанию, сами узлы остаются.

**Кому какие подписки.** Ключ подписки: `balancers` (только три балансировщика), `all` (балансировщики и все серверы пула), `b:<адрес>` (сборка). Список доступных подписок определяется по приоритету:
1. личный список пользователя (Пользователи → «Подписки»);
2. список тарифа, который пользователь оплатил последним (Сайт → Тарифы → «Подписки тарифа»; администратор может назначить тариф вручную);
3. список по умолчанию (вкладка «Подписки» → «Параметры пользователей по умолчанию», настройка `user_default_subs`, по умолчанию только `balancers`, см. 6j).
Адрес `/sub/<токен>` отдаёт всё, что доступно пользователю, одним списком. Подписка вне списка отвечает 403. В кабинете на сайте показываются только доступные подписки с QR-кодами; на страницах тарифов видно, что входит в каждый. Если у пользователя нет ни `balancers`, ни `all`, его ключ шлюза не выдаётся (в течение 30 секунд убирается из шлюза): остаются только сборки.

**Умолчания.** `user_default_subs` и `user_default_days` (срок в днях для пользователей, созданных в панели; 0 = без срока). Новые люди с сайта получают пробные дни из `site_trial_days` и список по умолчанию. Менять можно в панели, `vpnb set` или API.

**Статистика пользователя** (Пользователи → «Статистика», из таблицы аккаунтов тоже): онлайн сейчас и открытые подключения, скорость сейчас, трафик за сегодня / 7 / 30 дней / всё время (отдельно скачано и отправлено), число подключений, последняя активность и адрес, самый активный час, сколько раз и когда скачивалась подписка, ошибки подключений, график по дням (30 дней, UTC) и по часам (48 часов). API: `GET /api/users/<имя>/stats`.

**API:** `GET /api/catalog`; `POST/PUT/DELETE /api/custom-nodes[/id]`; `POST/PUT/DELETE /api/bundles[/id]`; `POST /api/users/<имя>/subs` (`{"subs": [...]}` или `null` = вернуть на тариф/умолчание); `POST /api/users/<имя>/plan` (`{"plan_id": N}`, 0 = снять); `PUT/POST /api/plans` теперь принимает `subs` (список или `null`).

**Ограничения.** Свои узлы не проверяются (если сервер упал, подписка будет отдавать его как есть). Статистика по часам хранится 180 дней. Смена подписок пользователя применяется в шлюзе в течение 30 секунд.

## 6j. Внешние серверы, режимы и категории (итерация 14, версия 3.2.0)

Вкладка **«Серверы»** — отдельная панель для серверов, которые не входят в балансировщик. Балансировщик работает как раньше (пул, проверки, оценка, failover) и внешних серверов не касается: они не проверяются и не участвуют в выборе узла.

**Как добавлять.** Одиночный сервер ссылкой (vless, vmess, trojan, ss, hysteria2) или целую подписку (адрес подписки; серверы загружаются сами и обновляются каждые `sub_refresh`, кнопка «Обновить» делает это сразу). Исчезнувшие из подписки серверы живут ещё `node_grace`. Ссылки серверов и адреса подписок хранятся в базе и нигде не показываются: ни в панели, ни через API, ни пользователям (видны название, тип, адрес сервера и хост подписки; заменить можно, вставив новое значение).

**Режим каждого сервера или подписки:**
- «Отдать ссылку» (`direct`): пользователь получает в подписке ссылку на этот сервер и подключается к нему напрямую;
- «Через основной сервер» (`via`): пользователь получает в подписке отдельный ключ шлюза для этого сервера (в клиенте он называется по имени сервера). Шлюз принимает его на том же порту 443 и пересылает трафик на внешний сервер; настоящая ссылка пользователю не раскрывается. Правила фильтра (блокировки, страны, домены) действуют и на такой трафик. Статистика и онлайн считаются на пользователя, в сеансах режим показан как «внешний сервер №N». Если sing-box отвергает ссылку сервера, он исключается, остальные продолжают работать.

Режим подписки распространяется на все её серверы; у одиночных серверов он свой.

**Категории.** Подписка пользователя собирается из категорий (`/sub/<токен>/b/<адрес>`). В категорию входят: основной сервер (отметка «3 балансировщика»), отдельные серверы, целые подписки в любом сочетании. Категорий можно создавать сколько угодно, менять и удалять. Встроенная категория «Основная» (ключ `balancers`) содержит только 3 балансировщика (текущий, лучшая скорость, лучший пинг) и является группой по умолчанию: `user_default_subs` по умолчанию = `[balancers]` (раньше было `balancers` + `all`; уже сохранённые настройки не меняются). Ключ `all` (балансировщики и все серверы пула) остаётся и выбирается вручную.

**Основной сервер как концентратор.** Если в категориях пользователя нет отметки «3 балансировщика», балансировщик ему не выдаётся: ключ шлюза у него только для серверов в режиме «через основной сервер» (или вообще нет, если все серверы в режиме «отдать ссылку»; тогда основной сервер просто раздаёт подписку). Кому какие категории доступны, по-прежнему задаётся пользователю, тарифу или по умолчанию.

**API:** `GET /api/catalog` (теперь с `sources`); `POST/PUT/DELETE /api/custom-nodes[/id]` (поле `mode`); `POST/PUT/DELETE /api/ext-sources[/id]` (`name`, `url`, `mode`, `enabled`); `POST /api/ext-sources/<id>/refresh`; `POST/PUT/DELETE /api/bundles[/id]` (поля `main`, `nodes`, `sources`).

**Одна ссылка (3.3.0).** Пользователю в панели и в кабинете показывается одна ссылка: `/sub/<токен>`. В ней всё, что входит в выбранные для него категории; отдельных ссылок на балансировщики и категории нет. Что именно входит, видно в панели под ссылкой.

**Подписки с множеством выходов.** Серверы подписки, отличающиеся только названием (один вход, много выходов), импортируются все, а не склеиваются в один. Поля ввода ссылки и адреса подписки показывают текст (не скрывают); сохранённые значения по-прежнему нигде не показываются.

**Все тарифы сразу.** Вкладка «Сайт» → «Все тарифы сразу»: заменить, добавить или убрать выбранные категории у всех тарифов; по отметке сбрасываются и личные списки пользователей. API: `POST /api/plans/bulk-subs` (`{"mode":"set|add|remove","subs":[...],"reset_users":false}`).

**Обновление.** Схема БД дополняется сама. Старые образы шлюза не знают ключей `имя~x<номер>`, но контроллер сам сводит их статистику к пользователю. Изменение списков и режимов применяется в шлюзе в течение 30 секунд.

## 6k. DNS и Cloudflare: домен без IP, автообновление записи (версия 3.4.0)

**Что нужно в DNS.** Одна запись типа A: `nvrk.ytc-srv.org` → публичный IP сервера. В Cloudflare у неё должно быть **«DNS only» (серое облако), не «Proxied»**: VLESS+Reality на 443 и WireGuard через прокси Cloudflare не работают, а сертификат сайта выпускается через порт 80 напрямую. Больше записей не нужно (сайт, подписки и ссылки используют тот же домен). Если хотите отдельные имена (например `sub.`), добавьте их так же серыми A-записями и укажите в `ddns_names`.

**Где ещё мог оставаться IP.** Адрес подписки `sub_public_url`, который записывали старые установщики (`http://IP:8081`). Начиная с 3.4.0, если задан `domain`, IP в этом адресе автоматически заменяется доменом (порт сохраняется). Ссылки на балансировщик и сайт строились на домене и раньше. IP-адреса остаются только в ссылках чужих серверов, которые вы добавили в режиме «отдать ссылку»: там адрес задаёт их владелец. В режиме «через основной сервер» пользователь видит только ваш домен.

**HTTPS для подписок (3.5.0).** Подписки отдаются сайтом по HTTPS с тем же сертификатом Let's Encrypt, что и сайт (`https://домен:8443/sub/<токен>`, на 443 при включённом «сайт на порту 443»). Как только сертификат выпущен, адрес подписки в панели и в кабинете автоматически становится https, а старый http-порт 8081 перенаправляет (308) на https-адрес, поэтому уже выданные ссылки продолжают работать. Для этого включите сайт (вкладка «Сайт») и откройте порты 80 и 8443. Явный `sub_public_url: https://...` или `sub_tls_cert`/`sub_tls_key` по-прежнему работают.

**Автообновление записи (Cloudflare).** Если у сервера меняется IP, контроллер сам обновляет A-запись. В config.yaml:
```yaml
cloudflare_token: "…"        # API-токен
# ddns_names: [nvrk.ytc-srv.org]   # по умолчанию: domain
# ddns_interval: 5m
# cloudflare_proxied: false        # оставьте false
```
Токен: Cloudflare → My Profile → API Tokens → Create Token → шаблон «Edit zone DNS»; права `Zone: Read` и `DNS: Edit`, ресурс: зона вашего домена (`ytc-srv.org`). Контроллер определяет внешний IP (api.ipify.org, icanhazip.com, ifconfig.me), находит зону сам, создаёт запись, если её нет, или обновляет, если IP изменился. Об изменении и об ошибках приходит сообщение в Telegram. После правки config.yaml: `docker compose restart balancer`. Токен хранится только в config.yaml и нигде не показывается.

## 6l. Блокировки, форум, резервные копии и балансировщик «по трафику» (версия 3.6.0)

### Блокировка пользователя
У пользователя есть причина блокировки: **неуплата** (`unpaid`), **бан** (`ban`) или **другое** (`other`), плюс текст причины (до 300 символов).
Заблокированный пользователь убирается из шлюза в течение 30 секунд, его ссылка подписки перестаёт отдавать серверы,
в кабинете сайта виден красный баннер с причиной.
- Панель: вкладка «Пользователи», кнопки «Заблокировать» / «Разблокировать». CLI: `vpnb block ИМЯ ban Спам`, `vpnb unblock ИМЯ`.
  API: `POST /api/users/ИМЯ/block` с телом `{"kind":"ban","reason":"…"}`, `POST /api/users/ИМЯ/unblock`.
- **Неуплата снимается сама**, когда платёж подтверждён (`MarkPaid`). Бан и «другое» платёж не снимает.
- **Бан закрывает ещё и вход на сайт** (аккаунт помечается заблокированным, сессии обрываются); при входе человек видит причину.
- Окончание срока подписки по-прежнему работает отдельно как автоматическая «мягкая» блокировка.

### Форум для баг-репортов и вопросов
Раздел `/forum` на сайте: темы видят только вошедшие пользователи, автор показан как «Пользователь #N» (почта и имя VPN не раскрываются).
Типы тем: ошибка, вопрос, идея, другое. Заголовок 3-120 символов, сообщение до 4000, не больше 10 сообщений в 15 минут от одного человека.
Пользователь не может писать в закрытую или скрытую тему.
Модерация в панели, вкладка «Форум» (счётчик тем, ждущих ответа): ответ от имени поддержки (помечается «Поддержка», пишет даже в закрытую тему),
закрыть/открыть, закрепить, скрыть тему или отдельное сообщение, удалить тему. API: `/api/forum/topics…`, `/api/forum/posts/ID/hide|show`.
Не публикуйте в темах ссылки подписки и ключи: об этом напоминает форма.

### Резервные копии
В копию входят: пользователи (с блокировками), тарифы, аккаунты сайта и платежи, внешние серверы/подписки/категории, WireGuard, форум,
трафик и настройки панели из базы (кроме токена панели). Не входят: узлы и история проверок (пересобираются сами), сессии сайта, кэш сертификатов, `config.yaml`
(его храните отдельно: в нём ключи Reality и токены).
- Формат: JSON + gzip, имя `vpnb-backup-v3.6.0-ГГГГММДД-ЧЧММСС.json.gz`; с `backup_password` файл шифруется (AES-256-GCM, ключ из пароля через scrypt) и получает суффикс `.enc`.
  **Копия содержит ключи и хеши паролей**, поэтому без пароля её надо хранить как секрет.
- Автоматически каждые `backup_interval` (по умолчанию 24h; отрицательное значение выключает), хранится `backup_keep` (14) штук в `backup_dir`
  (по умолчанию `/var/lib/balancer/backups`, это том `balancer-data`: для защиты от потери сервера скачивайте копии).
  С `backup_telegram: true` и паролем зашифрованная копия отправляется ещё и в чат Telegram.
- Панель: вкладка «Бэкапы» (создать, скачать, восстановить, удалить, загрузить файл). CLI: `vpnb backup`, `vpnb backups`, `vpnb restore ИМЯ|ПУТЬ`.
  API: `GET/POST /api/backups`, `GET/DELETE /api/backups/ИМЯ`, `POST /api/backups/ИМЯ/restore`, `POST /api/backups/restore` (тело = файл).
- Восстановление заменяет все перечисленные данные одной транзакцией (всё или ничего). Перед ним автоматически делается страховочная копия `…-before-restore`,
  она не удаляется ротацией. Перенос на новый сервер: установить, положить тот же `config.yaml`, загрузить файл копии.

### Балансировщик «по трафику»
Четвёртый режим рядом с «текущий», «лучшая скорость», «лучший пинг». По умолчанию **скрыт**: у пользователей остаются 3 балансировщика.
Включается в панели («Настройки» → «Балансировщик по трафику») или `vpnb set spread_mode true`; тогда четвёртая ссылка появляется в подписках, кабинете и панели.
Как работает: sing-box 1.11 не умеет взвешенный выбор, поэтому селектор режима переставляется. Шлюз считает байты сессий этого режима, контроллер приписывает их узлу,
который был выбран в это время, и раз в `spread_interval` (по умолчанию 60 с) переключает режим на узел лучшей группы (как у «скорости» и «пинга»), который нёс меньше всех (счётчики затухают с периодом полураспада 1 час).
Переход делается, только если новый узел несёт не более 80% нагрузки текущего и разница не меньше 1 МБ. Мёртвый или неподходящий узел заменяется сразу.
Это приближение: уже открытые соединения доживают на старом узле, новые идут на следующий, то есть нагрузка делится по очереди.
Ключ режима (`имя~spread`) работает в шлюзе всегда; видимость управляется только настройкой.
**Нужен новый шлюз** (счёт трафика по режимам): `bash install.sh update --gateway`; со старым шлюзом режим работает, но нагрузка не учитывается и узлы чередуются слабо.

## 7. Мониторинг и алерты

### 7.1. HTTP-интерфейс

Адрес по умолчанию: `http://127.0.0.1:8080` (на сервере). Авторизации нет, см. [безопасность](#10-безопасность).

| Путь | Что возвращает |
|---|---|
| `/healthz` | `ok` (HTTP 200), если sing-box работает; иначе 503. Используется в healthcheck Docker. |
| `/status` | JSON: `net_down`, `switches`, список узлов. |
| `/metrics` | Метрики в формате Prometheus. |

Поля узла в `/status`:

| Поле | Смысл |
|---|---|
| `tag` | Внутренний идентификатор (`n-` + 10 символов ID). |
| `name`, `server`, `type` | Из подписки. |
| `score` | Текущая оценка (0 значит узел не используется). |
| `latency_ms`, `jitter_ms` | Сглаженная задержка и разброс. |
| `success_rate` | Доля успешных проверок в окне (0..1). |
| `speed_kbps` | Последний замер скорости (0, если не мерился). |
| `quarantined` | Узел в карантине. |
| `current` | Через него сейчас идёт трафик. |
| `exit_country`, `exit_ip` | Измеренная страна и адрес выхода (пусто, пока не измерено). |
| `allowed` | Может нести трафик пользователей (`exit_country` известна и не в `blocked_exit_countries`). |

Полезные запросы (нужен `jq`):

```bash
# текущий узел
curl -s 127.0.0.1:8080/status | jq '.nodes[] | select(.current)'

# топ-10 по оценке
curl -s 127.0.0.1:8080/status | jq -r '.nodes | sort_by(-.score)[:10][] | "\(.score)\t\(.latency_ms)ms\t\(.name)"'

# сколько узлов живо
curl -s 127.0.0.1:8080/status | jq '[.nodes[] | select(.score>0)] | length'
```

### 7.2. Метрики Prometheus

| Метрика | Смысл |
|---|---|
| `balancer_nodes_total` | Узлов в пуле. |
| `balancer_nodes_healthy` | Узлов с оценкой больше 0. |
| `balancer_switches_total` | Число переключений с момента запуска. |
| `balancer_net_down` | 1, если у сервера нет базовой связности. |
| `balancer_node_score{tag}` | Оценка узла. |
| `balancer_node_latency_ms{tag}` | Задержка узла. |
| `balancer_node_speed_kbps{tag}` | Скорость узла. |
| `balancer_node_current{tag}` | 1 у текущего узла. |

Разумные алерты: `balancer_nodes_healthy == 0` дольше 2 минут; `rate(balancer_switches_total[1h]) > 6`
(слишком частые переключения); `balancer_net_down == 1`. Чтобы Prometheus достучался до `8080`, либо
запускайте его на этом же сервере, либо поставьте обратный прокси с паролем. Не открывайте 8080 в интернет.

### 7.3. Telegram-алерты

1. В Telegram напишите @BotFather, команда `/newbot`, получите токен.
2. Напишите своему боту любое сообщение.
3. Узнайте ID чата: откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id":...}`.
4. Впишите `telegram_token` и `telegram_chat` в `config.yaml`, перезапустите.

Какие алерты приходят:

| Алерт | Когда | Не чаще |
|---|---|---|
| ⚠️ Failover: A → B | Переключение с одного узла на другой | раз в минуту |
| 🔴 Все узлы недоступны | Нет ни одного узла с оценкой больше 0 (при проверенных узлах) | раз в 15 мин |
| ⚠️ Подписка ... не обновляется | 3 и более неудачных обновления подряд (в тексте адрес без токена) | раз в 6 ч |
| ⚠️ У сервера нет базовой связности | Не проходит TCP до `baseline_addrs` | раз в 30 мин |
| 🔴 Пул узлов пуст | Нет ни одного узла в БД после старта | раз в час |

### 7.4. История в БД

```bash
docker compose exec postgres psql -U balancer balancer
```

```sql
-- последние переключения
SELECT ts, from_node, to_node, reason FROM switches ORDER BY ts DESC LIMIT 20;

-- как вёл себя узел за сутки (подставьте ID из таблицы nodes)
SELECT date_trunc('hour', ts) h, avg(latency_ms) FILTER (WHERE ok) lat,
       count(*) FILTER (WHERE NOT ok) fails, count(*) n
FROM checks WHERE node_id = '...' AND ts > now() - interval '1 day' GROUP BY 1 ORDER BY 1;

-- узлы по названию
SELECT id, name, type, server, last_seen FROM nodes ORDER BY last_seen DESC;
```

Таблица `checks` автоматически очищается: хранятся последние 7 дней.

## 6m. Сеть серверов, режимы установки, конечные серверы и WireGuard-узел (версия 3.7.0)

### Режимы установщика (`--mode`)
| Режим | Что ставится | Папка | Команда |
|---|---|---|---|
| `default` | балансировщик и панель, как раньше | `/opt/vpn-balancer` | `vpnb` |
| `panel` | только панель: пользователи, тарифы, группы, сайт, форум, сеть серверов. Трафик пользователей не несёт | `/opt/vpn-panel` | `vpnb-panel` |
| `balancer-only` | только балансировщик (шлюз, проверки, выбор узла, выдача подписок на порту 8081). Пользователей берёт из панели | `/opt/vpn-balancer` | `vpnb` |
| `end-node` | конечный сервер с протоколами на выбор, без балансировки и без базы данных | `/opt/vpn-endnode` | `vpnb-node` |
| `wg` | WireGuard-узел: подписка, один выбранный сервер, устройства дома выходят только через него | `/opt/vpn-wg` | `vpnb-wg` |

Режим запоминается в `<папка>/.mode`; `update`, `status`, `uninstall` без `--mode` находят установку сами. Примеры:
```
bash install.sh --mode panel --domain vpn.example.com -y
bash install.sh --mode balancer-only --domain de.example.com --panel-url https://vpn.example.com --panel-token vpnb_… --name Берлин -y
bash install.sh --mode end-node --domain fi.example.com --panel-url https://vpn.example.com --panel-token vpnb_… --inbounds vless-reality,hysteria2:8443,trojan -y
bash install.sh --mode wg --sub https://provider/sub/xxx --domain home.example.com --lan 192.168.0.0/24 --server Финляндия -y
```
Токен и готовую команду даёт панель: вкладка **«Сеть»** -> «Создать и получить команду». Токен показывается один раз (в базе только его хеш);
«Новый токен» выпускает другой, прежний перестаёт работать сразу.

### Как серверы связаны с панелью
Каждый сервер раз в `sync_interval` (30 с) делает `POST /api/sync` на адрес панели (сайт, HTTPS) с заголовком `Authorization: Bearer <токен>`. Он сообщает версию,
адрес, шаблоны своих ссылок и суммарный трафик пользователей, а в ответ получает **список пользователей, которым разрешён доступ к серверам этого вида**:
не заблокирован, включён, срок не истёк, в подписке есть `balancers` (для балансировщика) или `servers` (для конечного сервера), либо `all`.
Это даёт главное свойство сети: **пользователь, заблокированный в панели, пропадает из списка на всех серверах** (не более чем через `sync_interval` + 5-30 секунд),
а его текущие соединения закрываются:
- на балансировщике пользователь отключается, конфигурация шлюза обновляется, соединения закрываются через `drain_urgent` (5 с);
- на конечном сервере sing-box перезапускается без пользователя, соединения обрываются сразу.
Если панель недоступна, сервер работает с последним полученным списком (конечный сервер хранит его на диске) и шлёт тревогу. Ограничение: пока панель недоступна, блокировки не доходят.

Ссылки серверов добавляются в подписки пользователя: балансировщики во все места, где отдаются балансировщики (`balancers`, `all`, категории с основным сервером),
конечные серверы в новую подписку **`servers`** («Конечные серверы») и в `all`. Ключ пользователя на балансировщике тот же, что на главном (`uuid`), токен подписки совпадает.
Трафик, о котором сообщают серверы, складывается в статистику пользователя (заголовок подписки и кабинет). Конечные серверы трафик по пользователям не считают (ограничение).

### Конечный сервер
Конфигурация `endnode.yaml` (создаётся установщиком, команда `vpnb-node init` внутри контейнера). Протоколы (`vpnb-node add ТИП [--port N] [--name ИМЯ]`):
`vless-reality`, `vless-tls`, `vless-ws`, `vless-grpc`, `trojan`, `trojan-ws`, `vmess-ws`, `shadowsocks` (AEAD), `hysteria2`, `tuic`.
Reality-ключи создаются автоматически. Сертификат (`tls.mode`): `self-signed` (по умолчанию; в ссылки добавляется «пропускать проверку»), `file` (свои `cert`/`key`) или `acme` (Let's Encrypt, нужен домен и свободный порт).
`vpnb-node inbounds | del ИМЯ | links [ПОЛЬЗОВАТЕЛЬ] | check`. Изменения файла подхватываются за несколько секунд. Каждый порт занят одним протоколом (TCP и UDP считаются отдельно).
Пароли протоколов выводятся из ключа пользователя (`uuid`), поэтому отдельных паролей хранить не нужно. Пользователям закрыты частные адреса сети сервера (`allow_private: true` снимает запрет).
Для TUIC в ссылках пул-парсер балансировщика поддержки не имеет, клиентские приложения понимают.

### WireGuard-узел
`wgnode.yaml`: адрес подписки, выбранный сервер, порт и сеть туннеля, устройства. Работает так: устройство в сети `192.168.0.0/24` -> роутер -> WireGuard -> узел -> **выбранный сервер подписки**.
Прямого выхода нет: если сервер не выбран или исчез из подписки и в кэше его нет, трафик отклоняется. Команды `vpnb-wg`:
`servers` (список подписки), `select ИМЯ` (имя или его часть), `status`, `peer add|del|list ИМЯ [--lan СЕТЬ]`, `peer config ИМЯ` (профиль для телефона и ноутбука), `peer router ИМЯ` (скрипт RouterOS).
Подписка перечитывается раз в 30 минут; выбранный сервер ищется по стабильному идентификатору, переименование в подписке не ломает выбор.

### Роли в config.yaml
`role: full` (по умолчанию), `role: panel` (нет шлюза и проверок, сайт слушает 443), `role: balancer` (`panel_url`, `panel_token`, `panel_insecure`, `sync_interval`, `server_name`).
Для роли `panel` достаточно `reality.private_key` (любая длинная случайная строка: из неё выводятся секреты сессий).

### Заголовок подписки
Каждая выдача подписки содержит `subscription-userinfo: upload=…; download=…; total=0; expire=…` (`total=0` значит «без лимита», так как квот трафика нет),
название подписки (`profile-title`) — «название VPN из панели · ник» (например «VPN · Миша»); трафик и срок показывают сами приложения в строке трафика (из `subscription-userinfo`).

### Сайт: дизайн, инструкции, вложения
Тема и палитра выбираются посетителем (меню 🎨, запоминается в cookie) и по умолчанию в панели («Сайт»: `site_theme`, `site_palette`, `site_accent`).
Раздел `/help` с инструкциями редактируется в панели («Сайт» -> «Инструкции»: простая разметка `##` заголовки, списки, `**жирный**`, `` `код` ``, ссылки http/https); 6 страниц созданы заранее.
Форум: картинки (PNG, JPEG, GIF, WebP; не SVG) до **1 МБ** и файлы до **10 МБ**, не больше 5 вложений в сообщении, квота 100 МБ на пользователя. Включаются отдельно для пользователей (`forum_images`, `forum_files`); администратор в панели прикладывает любое без ограничений.
Файлы отдаются только вошедшим, без исполнения (`nosniff`, песочница CSP); в резервную копию входят, пока общий объём до 256 МБ.

## 6n. Сервис: два канала, статистика сети, баланс, рефералы, Telegram (версия 3.8.0)

### Цель
Проект - не только балансировщик, а основа VPN-сервиса: люди регистрируются на сайте, платят, получают подписку, приглашают друзей и пользуются ботом; администратор видит всё в одной панели. Оплата пока заглушка (`manual` и `stub_auto`), но всё вокруг неё уже работает так, как будет с настоящей платёжной системой.

### Ник и название подписки
У каждого пользователя есть **номер** (`id`, последовательный, не меняется), **имя** (ключ в шлюзе и в статистике, не меняется) и **ник** (можно менять). Ник меняется в панели («Пользователи» -> «Сменить ник»), в кабинете, командой `nick ИМЯ НИК` и API `POST /api/users/{имя}/nick`.
Название подписки в приложении: `название VPN из панели · ник` (разделитель - точка по центру строки, `·`). Строка трафика приложения показывает использованное и **дату окончания подписки** (`subscription-userinfo: upload; download; total=0; expire`). Названия с трафиком в заголовке больше нет, `sub_title_stats` удалён.

### Привязка подписки к серверу
Подписка `s:<id>` даёт ссылки одного зарегистрированного сервера (вкладка «Сеть»). Её можно выбрать у тарифа, группы или пользователя так же, как `balancers`, `servers`, `all`. Адрес `/sub/{токен}/s/{id}`. Сервер получает в списке синхронизации только тех, кому он положен: пользователь с `s:3` не появится на сервере 4.

### Два канала балансировщика
- **Канал админов** - как раньше: подписки `subscriptions`, режимы «текущий», «скорость», «пинг» (и «по трафику» при `spread_mode`).
- **Канал пользователей** - свой **пул узлов**: `users_subscriptions` (панель: «Настройки» -> «Канал пользователей»; CLI `set users_subscriptions ...`). Свои селекторы шлюза `proxy-u`, `proxy-u-speed`, `proxy-u-ping`, свои ключи (`имя~u`, `имя~u-speed`, `имя~u-ping`), проверки и выбор лучшего узла только внутри своего пула. Узел, который есть в обоих списках, участвует в обоих.
- Канал человека - поле `users.channel` (`admin` по умолчанию). Люди с сайта попадают в канал `site_channel` (по умолчанию `users`); меняется в панели у каждого пользователя, командой `channel ИМЯ admin|users` и API `POST /api/users/{имя}/channel`. Человек получает ссылки только своего канала; в обычной подписке (`all`) он видит узлы только своего пула.
- Пока список `users_subscriptions` пуст, канал пользователей работает на пуле админов (ничего не ломается при обновлении).
- Основной балансировщик админов не выбирает узлы, которые есть только в списке пользователей, и наоборот.
- На удалённых балансировщиках (`role: balancer`) канал человека передаётся вместе со списком пользователей.

### Статистика всей сети в одном месте
Трафик по пользователям собирается на **всех** серверах и складывается на главной панели:
- балансировщики присылают суммарные счётчики пользователей (как в 3.7.0);
- **конечные серверы теперь тоже**: для каждого пользователя в sing-box создаётся свой исходящий `u-<имя>`, а локальный Clash API (127.0.0.1:`stats_port`, по умолчанию 29090, пароль случайный на каждый запуск) отдаёт байты открытых соединений. Счётчики хранятся в `work_dir/traffic.json`, переживают перезапуск и уходят панели с очередной синхронизацией. Погрешность: байты, прошедшие между последним опросом (раз в 2 с) и закрытием соединения, не учитываются;
- панель считает прирост отчётов по часам (`server_traffic_hourly`), поэтому графики «по дням», «по часам», «за 7 и 30 дней» и итоги пользователей включают все серверы;
- по каждому пользователю отдельно видно, сколько через какой сервер (статистика пользователя: «По серверам»); на «Обзоре» и в «Сети» - «Трафик всей сети» с разбивкой по серверам и итогом (`GET /api/traffic/network`).

### Баланс, пополнение, промокоды
- **Баланс** аккаунта (в копейках, не уходит ниже нуля) и история операций. Кабинет: баланс, «Пополнить» (через ту же заглушку оплаты), «Оплатить с баланса» на странице оплаты, промокод. Администратор меняет баланс во вкладке «Сервис» (`POST /api/accounts/{id}/balance`).
- **Промокоды** (вкладка «Сервис», `GET/POST /api/promos`, `DELETE /api/promos/{код}`): `percent` - скидка при оплате тарифа, `days` - дни доступа, `balance` - деньги на баланс. Лимит использований, срок действия, один раз на аккаунт. Подбор кодов ограничен по частоте.
- **Реферальная программа**: ссылка `/r/КОД` в кабинете; когда приглашённый **впервые оплатит подписку**, пригласивший получает `ref_bonus_days` дней (по умолчанию 7) и/или `ref_bonus_percent` процентов от платежа на баланс, приглашённый - `ref_invitee_days` дней. Награда выдаётся один раз.
- **Обратный вызов платёжной системы** `POST /pay/webhook/{провайдер}`: тело `{"payment_id":N,"status":"paid|canceled","amount_cents":N,"ext_id":"..."}`, заголовок `X-Signature` - hex HMAC-SHA256 тела с ключом `pay_webhook_secret`. Без ключа адреса нет (404). Повтор безопасен. Подключение настоящей оплаты: реализовать `PaymentProvider.Start` и указывать обратный вызов на этот адрес.

### Telegram-бот
`bot_token` (от @BotFather) в панели («Сервис»). Бот работает через long polling: входящий порт не нужен; `bot_api_url` - адрес API (прокси). Человек получает в кабинете код привязки (15 минут) и отправляет боту `/start КОД`. Команды: `/status`, `/sub`, `/plans`, `/buy НОМЕР [ПРОМОКОД]` (с баланса, если хватает, иначе через оплату сайта), `/balance`, `/promo КОД`, `/ref`, `/unlink`. Чат привязан к одному аккаунту; заблокированный аккаунт ничего не получает. Токен не попадает в журнал.

### Резервные копии и обновление
В копии входят `balance_ops`, `promos`, `promo_uses`, `server_traffic_hourly`. Схема обновляется сама (`ALTER ... IF NOT EXISTS`); существующие пользователи остаются в канале админов. Шлюз пересобирать не нужно.

## 8. Повседневная эксплуатация

| Задача | Команда |
|---|---|
| Логи в реальном времени | `docker compose logs -f balancer` |
| Последние 200 строк | `docker compose logs --tail 200 balancer` |
| Перезапуск после правки config.yaml | `docker compose restart balancer` |
| Остановить всё | `docker compose down` (данные сохраняются) |
| Статус контейнеров | `docker compose ps` |
| Добавить подписку | Допишите URL в `subscriptions`, `docker compose restart balancer` |
| Убрать подписку | Удалите URL из конфига и перезапустите. Её узлы уйдут из пула через `node_grace` (48 ч). Чтобы убрать сразу: `DELETE FROM nodes WHERE source = '...'` |

### Обновление кода

**Через установщик (бесшовно):** замените `install.sh` на новый и выполните

```bash
sudo bash install.sh update
```

Настройки, пользователи и данные сохраняются. Пересобирается и перезапускается **только контроллер**: шлюз с
открытыми соединениями пользователей не трогается. На это время (около 5-10 секунд) приостанавливаются проверки узлов и
failover, остальное работает. Если шлюз или sing-box изменились в новой версии, установщик об этом скажет и предложит
`sudo bash install.sh update --gateway`: это перезапускает шлюз и **обрывает соединения на 2-5 секунд**
(клиенты переподключаются сами). Делайте это в тихое время и только когда нужно.

Установка старой версии с одним контейнером при первом `update` переводится на отдельный шлюз (один раз, с паузой в несколько секунд).

**Вручную:**
```bash
docker compose build balancer && docker compose up -d --no-deps balancer     # только контроллер, без обрыва
docker compose build gateway && docker compose up -d --no-deps gateway       # шлюз (обрыв на 2-5 с)
```

Данные (БД, состояние шлюза) лежат в томах и переживают пересборку. Схема БД создаётся и дополняется
автоматически (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`).

### Обновление версии sing-box

В `Dockerfile` первая строка `ARG SINGBOX_VERSION=1.11.4`. Версия закреплена осознанно: формат конфига
проверен именно на ней. Перед сменой версии прогоните тесты с новым бинарником (раздел 11). Ветка 1.12+
может менять синтаксис.

### Резервное копирование

Важно сохранять: `config.yaml`, `.env` и базу (там пользователи и их UUID: потеряв их, вы потеряете все
выданные ссылки).

```bash
docker compose exec -T postgres pg_dump -U balancer balancer | gzip > balancer-$(date +%F).sql.gz

# восстановление в пустую базу
gunzip -c balancer-2026-09-30.sql.gz | docker compose exec -T postgres psql -U balancer balancer
```

Только таблица `users` достаточна, чтобы сохранить ссылки: узлы и проверки восстановятся сами.

### Перенос на другой сервер

Перенесите `config.yaml`, `.env` и дамп БД, поднимите `docker compose up -d --build`, восстановите дамп.
Если `public_host` изменился, выдайте пользователям новые ссылки (`bal users`).

### Смена ключей Reality

Сгенерируйте новую пару, обновите `config.yaml`, перезапустите. **Все пользователи получают новые ссылки.**
Делайте это только при компрометации приватного ключа.

## 9. Диагностика проблем

Порядок действий: `docker compose ps` → `docker compose logs --tail 200 balancer` → `curl 127.0.0.1:8080/status`.

| Симптом | Вероятная причина и что делать |
|---|---|
| Контейнер перезапускается, в логе `config: X is not set` | Не заполнен обязательный параметр или остался плейсхолдер `<...>`. Заполните `X`. |
| `config: subscriptions is empty` | Нет ни одной подписки в `config.yaml`. |
| `initial config: sing-box check failed ...` | Проблема не в узле, а в общих настройках (чаще всего неверные ключи Reality). Проверьте `reality.*`, читайте текст ошибки sing-box. |
| Ошибка подключения к БД при старте | Неверный пароль в `database_url` или спецсимволы в пароле. Пароль должен совпадать в `.env`, используйте только буквы и цифры. |
| `/healthz` отвечает 503 | sing-box не запущен или перезапускается. Смотрите строки `core:` в логе. |
| В `/status` пусто или узлов мало | Подписки не скачались (ищите строки `subs:` в логе, например `subs: host: 120 nodes` или `(fail #N)`, и алерт о подписке), либо узлы отброшены как неподдерживаемые. Проверьте подписку вручную: `curl -s -A sing-box URL \| head -c 500`. |
| Все узлы с `score: 0` сразу после старта | Нормально первые минуты: оценка появляется после первого цикла tier2 (~3 мин). |
| Все узлы с `score: 0` долго | Проверьте `net_down` в `/status`. Если `false`, а узлы мертвы, возможно, сервер не может добраться до `probe_urls` через узлы. Проверьте узел вручную (раздел ниже). Если `net_down: true`, проблема в сервере. |
| Клиент не подключается | Проверьте: порт 443 открыт (`ufw`, файрвол хостера), `public_host` правильный, ключи и `short_id` в ссылке совпадают с конфигом, пользователь не отключён (`bal users`), прошло 2-3 минуты после `adduser`. |
| В логе `REALITY: processed invalid connection`, клиент получает EOF | Если ключи, short_id и SNI совпадают, а клиент это свежий Xray (v2rayNG, Hiddify): смените Fingerprint в профиле с `chrome` на `ios` (с `chrome` свежие клиенты Xray не проходили проверку, с `ios` проходят; вероятная причина постквантовое приветствие). Иначе: Шлюз не признал клиента как Reality-клиента и отдал ему «настоящий» сайт-маскировку. Проверьте: (1) ключи: `public_key` в ссылке должен быть парой к `private_key` в конфиге, `short_id` совпадает; после смены ключей нужны новые ссылки; (2) клиент поддерживает Reality и `flow=xtls-rprx-vision`; (3) сайт `handshake_server` поддерживает TLS 1.3 и X25519 с вашего сервера: `echo \| openssl s_client -connect www.microsoft.com:443 -servername www.microsoft.com -tls1_3 -groups X25519 2>&1 \| grep -E "Protocol\|Cipher"`; если сайт не отвечает или режется, выберите другой (проверенные кандидаты в разделе 11a). Быстро проверить связку ключей и сайт можно скриптом `smoke-test.sh` (предпроверка Reality). |
| Все узлы `allowed: false`, пользователи без интернета, алерт «Нет допустимых узлов» | Выход всех узлов в запрещённой стране или страна не определилась. Смотрите `exit_country` в `/status` и строки `geo:` в логе. Если страна не определяется, проверьте `geo_urls` (доступны ли они через узлы). Временно можно сузить `blocked_exit_countries` или поставить `exit_check: false`, но тогда пользователь может выйти в цензурируемой стране. |
| Узел из подписки есть, но в подписке пользователя его нет | Узел ещё не проверен, выход в запрещённой стране, или он не перекачивался после обновления версии (ссылка сохраняется при очередной загрузке подписок, до 30 минут). |
| Клиент подключился, но интернета нет | Смотрите в `/status`, есть ли `current: true` и `score > 0`. Если нет живых узлов, трафик отклоняется. Если узел текущий и живой, проблема у самого узла. |
| Частые переключения | Узлы нестабильны. Увеличьте `switch_confirm` или `switch_margin`. Посмотрите `SELECT * FROM switches ORDER BY ts DESC`. |
| Переключений нет, хотя есть лучший узел | Так и задумано: нужны margin 1,15 и 3 цикла подряд. |
| Соединения рвутся раз в несколько минут | Перезагрузки sing-box из-за изменения узлов в подписках или добавления пользователей. Проверьте в логе `core: config reloaded`. Если подписка часто меняет набор узлов, увеличьте `min_reload_interval`. |
| Алерт «подписка не обновляется» | Проверьте ссылку `curl` с сервера; провайдер мог заблокировать IP сервера или сменить токен. |
| Узел из подписки не появился | Формат не поддерживается (раздел 6.1) или sing-box его отверг (строка `rejected by sing-box check`). |

**Проверить узел вручную** (найдите `tag` в `/status`, логин проб `probe-<tag>`; пароль меняется при каждом
запуске и хранится только в памяти, поэтому проще смотреть результаты в `/status` и в таблице `checks`):

```sql
SELECT ts, tier, ok, latency_ms, target, error
FROM checks WHERE node_id = (SELECT id FROM nodes WHERE name = 'Имя узла')
ORDER BY ts DESC LIMIT 20;
```

Поле `error` покажет причину (таймаут, отказ соединения, ответ 4xx/5xx).

## 10. Безопасность

- **Порт 8080 без авторизации.** В `docker-compose.yml` он проброшен только на `127.0.0.1` сервера. Не меняйте
  на `0.0.0.0` и не открывайте в файрволе. Для удалённого доступа используйте SSH-туннель
  (`ssh -L 8080:127.0.0.1:8080 server`) или обратный прокси с паролем.
- **Секреты.** `.env` и `config.yaml` содержат пароль БД, приватный ключ Reality и токен Telegram. Права
  `chmod 600`, не кладите в git.
- **Токены подписок** в логи и алерты не попадают (в сообщениях остаётся только домен). Но они лежат в
  `config.yaml`.
- **Все пользователи выходят через один узел.** Трафик ваших пользователей видит оператор узла. Выбирайте
  подписки, которым доверяете.
- **Нет узлов значит нет доступа.** Если пул пуст или все узлы мертвы, трафик пользователей отклоняется, а не
  уходит напрямую с сервера, поэтому IP сервера не раскрывается.
- **Один публичный порт.** Снаружи открыт только 443 (Reality). База и Clash API недоступны извне.

## 11a. Сквозной тест на тестовом сервере

Скрипт `smoke-test.sh` поднимает систему целиком на одном сервере и проверяет её как настоящий пользователь.
Всё идёт через loopback, внешние порты не нужны. Требуется root, Docker с compose v2, python3, curl.

```bash
unzip vpn-balancer-fixed.zip && cd vpn-balancer
bash smoke-test.sh                  # на локальных тестовых узлах (около 8-10 минут, первая сборка образа дольше)
bash smoke-test.sh 'https://...'    # то же + в конце ваша реальная подписка (ещё 4-5 минут)
bash smoke-test.sh --cleanup        # удалить контейнеры, тома и временные файлы теста
```

Что делает скрипт: генерирует ключи Reality, поднимает PostgreSQL и балансировщик (отдельный
`docker-compose.smoke.yml`, host-сеть), три живых тестовых узла shadowsocks (роль VPN-провайдера) и один
мёртвый, локальную тестовую подписку. Затем создаёт пользователя и подключается к шлюзу настоящим клиентом
sing-box по VLESS+Reality.

| Что проверяется | Критерий |
|---|---|
| Reality без балансировщика (предпроверка) | отдельный сервер и клиент sing-box с теми же ключами проходят рукопожатие; перебираются сайты-маскировки (`www.microsoft.com`, `www.cloudflare.com`, `www.apple.com`, `dl.google.com`, `addons.mozilla.org`) и, при неудаче, отпечатки клиента; для каждого сайта проверяется TLS 1.3 с сервера; выбирается рабочий `handshake_server` |
| Сборка образа, `go vet`, путь к sing-box | образ собирается, `/usr/local/bin/sing-box` на месте |
| Подписка и пул | узлы загружены, мёртвый узел имеет оценку 0, один текущий |
| Метрики и БД | `/healthz`, `/metrics`, записи в `checks` и `switches` |
| Пользователь | `adduser`, `users`, клиентская ссылка рабочая |
| Реальный клиент | HTTP 204 через шлюз на двух сайтах |
| Failover | апстрим текущего узла остановлен: переключение на другой и восстановление трафика, время и число сбойных запросов в сводке |
| Возврат узла | поднятый узел снова получает оценку больше 0 |
| Смена подписки | новый узел появляется, sing-box перезагружается, клиент продолжает работать |
| Tier 3 | скорость измерена |
| Перезапуск контроллера | продолжает с того же узла, клиент работает |
| `deluser` | отключённый пользователь больше не проходит |
| `go test` | все 44 теста (юнит и интеграционные) проходят в контейнере |

Если предпроверка Reality не проходит ни с одним сайтом, это значит, что проблема не в балансировщике, а в
окружении сервера или в самом sing-box. Подробности пишутся в `logs/reality-diag.log` отчёта.

Результат: сводка PASS/FAIL/INFO на экране и архив `/root/smoke-report.tgz` (сводка, логи контроллера и клиента,
`/status`, метрики, статистика проверок и ошибок из БД, конфиг без приватного ключа). Пришлите его разработчику.
Код возврата скрипта 0, если нет ни одного FAIL.

Типичный результат на здоровом сервере: failover и восстановление трафика за 10-12 секунд (клиент за это время
получает несколько неудачных запросов, дальше всё работает), новый пользователь начинает проходить через
шлюз примерно через 30 секунд.

Если скрипт остановился на проверке портов: тест использует 443, 8080, 9090, 2080, 55432, 18080-18081,
18388, 18390, 18392. Освободите их или напишите, какие заменить.

---

## 12. Ограничения

- Все пользователи выходят через один общий лучший узел (исключения: правила `direct`/`block` из раздела 6b).
- Страна выхода определяется внешними сервисами (`geo_urls`) и точна настолько, насколько точны их базы. Узел, чей выход
  «плавает» между странами, определяется по самому осторожному ответу.
- Правила по IP срабатывают только если клиент подключается к IP, а не к имени сайта (раздел 6b).
- Подписка пользователя содержит ссылки на серверы провайдера: выдавайте её по HTTPS и только доверенным людям.
- Добавление пользователей и смена набора узлов не обрывают соединений (раздел 6d). Обрыв на 2-5 с даёт только перезапуск самого шлюза и failover.
- Не разбираются Clash YAML, sing-box JSON, tuic, wireguard; отбрасываются транспорты xhttp/kcp/quic.
- `/status`, `/metrics`, `/healthz` без авторизации (слушайте только localhost); панель и `/api/*` требуют токена, но работают без TLS.
- Проверки мерят доступность и скорость с сервера, а не с устройства пользователя. Узел, хороший для сервера,
  может быть хуже для клиента в конкретной сети.
- Код проверен на локальных sing-box и PostgreSQL, но не на живых узлах провайдеров и не под нагрузкой
  сотен узлов. Первые дни следите за логами и `/status`.

## 13. Что присылать, если что-то не работает

1. Вывод `docker compose ps`.
2. Последние 200-300 строк `docker compose logs --tail 300 balancer` (токены подписок в логе скрыты, но
   проверьте на всякий случай).
3. Вывод `curl -s http://127.0.0.1:8080/status` (можно без имён узлов).
4. Что именно не работает: клиент не подключается, нет интернета, частые обрывы, что-то другое, и когда
   это началось.
5. Версия образа: `docker compose exec balancer sing-box version`.

Не присылайте: `.env`, `config.yaml` целиком, приватный ключ Reality, ссылки подписок и пользователей.


## Качество узлов, сервисы и диагностика пользователей (итерация 9)

**Скорость.** Для каждого узла хранятся последние 3 замера (скорость + время), время последней попытки и её ошибка, время последней проверки. Данные в таблице `nodes` (`speed_hist`, `speed_try_at`, `speed_err`, `check_at`, `svc`). В панели («Узлы») видно значение, дату замера и пометку «старое», если замеру больше суток; старый замер не даёт бонуса к оценке.

**Правило минимальной скорости.** `min_speed_kbps` (8000 = 8 Мбит/с, 0 = выкл.). Узел считается медленным, если два последних замера ниже порога и не старше 3×`speed_ttl`. Медленный узел не выбирается, пока есть другие; пользователи на нём переводятся на хороший без разрыва уже открытых соединений (причина переключения «slow»). Если медленны все, берётся лучший.

**Сервисы.** Настройка `services`: строки `имя = адрес, адрес` (`http://`, `https://`, `tcp://хост:порт`). Сервис «открывается», если ответила половина адресов. Проверка всех допущенных узлов раз в `service_interval` (1 ч), текущего узла - каждые 10 минут. `required_services` (по умолчанию `telegram`): два неудачных прохода подряд - узел исключается (причина «service»), если есть альтернативы. Неудача любого сервиса: −3 к оценке (максимум −15). Если проверка не удалась из-за перезагрузки sing-box или потери связи у самого сервера, результат не засчитывается.

**Настройки:** `min_speed_kbps`, `required_services`, `services` (панель → Настройки → «Качество узлов», `vpnb set`/`vpnb get`); в config.yaml также `speed_ttl`, `service_interval`.

**Пользователи.** `vpnb rmuser ИМЯ`, `DELETE /api/users/ИМЯ`, кнопка «Удалить» (с подтверждением): ссылка перестаёт работать в течение 30 секунд, счётчики трафика стираются. `vpnb deluser` по-прежнему только отключает.

**Консоль ошибок пользователя.** Шлюз связывает ошибки sing-box и блокировки правилами с пользователем по номеру соединения и хранит последние 300 событий на человека (в памяти, с запуска шлюза). Смотреть: Клиенты → «Диагностика», Консоль → «Ошибки пользователя», `vpnb logs user ИМЯ`, `GET /api/logs?src=user&user=ИМЯ`. Адреса обычных соединений не записываются. Счётчик ошибок виден в таблице «Клиенты».

**Если не работает Telegram:** `vpnb node ИМЯ_ТЕКУЩЕГО_УЗЛА` покажет, какие сервисы открываются через узел; `vpnb logs user ИМЯ` - что не удалось этому клиенту.
